# Детерминированные тесты конкурентности

Многопоточный прод-код (конвейер групп флаша L2: билдер-поток строит
группу N+1, консьюмер пишет группу N) нельзя проверять тестами на
таймерах: sleep-based тесты мигают, заваливаются под нагрузкой и ничего
не доказывают о порядке фаз. Волна P4 отработала два приёма, дающие
стабильные и честные тесты конкурентности.

## Приём 1: перехват событийной цепочки вместо таймеров

Суть: тест НЕ ждёт "достаточно долго", а перехватывает шаги конвейера и
управляет порядком явно через `Event`/`Lock`.

- Каждый значимый шаг конвейера подменяется или хукается так, что при его
  выполнении тест ставит `Event` (и при необходимости ждёт своего `Event`
  перед продолжением). Порядок "билдер построил N+1 до того, как
  консьюмер начал писать N" доказывается тем, что тест детерминированно
ставит два события в нужной последовательности, а не тем, что что-то
  успело произойти за sleep.
- Барьеры ожидания в прод-коде (`Condition` с таймаутом) в тесте
  убирают недетерминизм, а не создают его: тест сигналит условие сразу,
  без пауз.
- Проверка стабильности: прогон x3 - все зелёные. Мигающий тест
  конкурентности равен отсутствующему.

Прецедент: конвейер-тест волны P4 (перекрытие фаз билдера и писателя)
и drain-retry тест (ожидание drain pending при отказе резерва) -
детерминированы Event/Lock, стабильны x3
([P4-NOTES.md](../cases/boot-shutdown-io/P4-NOTES.md)).

Анти-паттерн, отработанный прочь: `time.sleep(N)` между фазами в тесте
- на CI/загруженной машине порядок фаз инвертируется, тест ловит не
инвариант, а гонку планировщика.

## Приём 2: source-привязка для защиты инварианта лока

Проблема: стресс-тест, гоняющий мутации общего счётчика из нескольких
потоков, может пройти даже когда одна из точек мутации ушла из-под лока
- окно гонки мала, зелёный прогон ничего не доказывает.

Решение: структурный assert через `inspect.getsource`:

- тест находит ФУНКЦИИ, содержащие мутации защищаемого состояния
  (обе точки мутации `_ssd_used`/`_dead_bytes` в волне P4);
- для каждой берёт `inspect.getsource(...)` и требует, чтобы исходник
  содержал захват лист-лока (`_account_lock`) - исходник, а не
  трассировку: трассировка мигает, исходник статичен;
- если мутация переезжает в функцию без лока или лок убирают при
  рефакторинге, тест краснеет сразу, без воспроизведения гонки.

Красность ДО доказывается точечным ревертом правки волны (метод -
[test-fails-before.md](test-fails-before.md)): убрать захват лока из
одной точки мутации -> source-тест красный.

Ограничение приёма: он защищает связь "мутация находится в функции,
которая берёт лок", но не сам порядок захвата - порядок всё равно
проверяется обычным поведенческим тестом или ревью.

## Сопутствующий урок волны P4: leaf-lock против self-deadlock

Пытаясь "закрыть" гонку добавлением лока, легко создать дедлок: если
лист-лок нереентрантен, а эвиктор вызывается из-под уже занятого
родительского пути, обкладывание эвиктора тем же локом - само-дедлок.
Проверять, что незалоченное чтение состояния - консервативное (может
отказать лишний раз, не может переполнить) и отказываться от лишнего
лока с обоснованием в коде, а не с молчаливым TODO.

## Сопутствующий урок волны P5: flush-локальная аккумуляция вместо общего счётчика

Задача "посчитать события рабочего потока и доложить владельцу" провоцирует
общий мутабельный счётчик (`self._counters`) - гонка на каждом инкременте.
Волна P5 (overflow-талли cap-эвикций `_FlushOverflow` в session_tier.py)
применила вместо этого:

- аккумулятор живёт на одной фазе флаша (flush-локальный объект), а не в
  долгоживущем состоянии стора;
- один писатель на поле: билдер-поток инкрементит records/bytes вне
  стора-лока, поток флаша - admitted; пересечения писателей исключены
  по построению;
- владелец читает сумму только после join билдера: join даёт
  happens-before, сумма видна без замка.

Цена - объект-посредник и слот с try/finally; выигрыш - ни одного лока на
горячем пути и отсутствие гонок по построению
([P5-NOTES.md](../cases/boot-shutdown-io/P5-NOTES.md)).

## Сопутствующий урок волны P7: settle-порядок относительно failable init

План задач может содержать no-op задачи (zero-job: банк без sub-read) в смеси
с рабочими, а бэкенд исполнения может быть failable и иметь fallback-путь,
повторяющий тот же протокол завершения. Ревью волны P7 (io_uring-чтение
FTW-банков) поймало MAJOR: zero-job задачи сеттлились ДО успешного создания
кольца; при отказе инициализации код уходил в пул-fallback и сеттлил те же
задачи второй раз -> двойной on_done = двойной pins.submit (сломан
пин-контракт).

Правило: при failable init с fallback-путём, повторяющим протокол завершения,
сеттл/колбэки ставятся только ПОСЛЕ точки выбора исполнителя; no-op задачи
не должны проходить через failable init - их сеттл либо инлайн (если fallback
там недостижим), либо после успешной инициализации.

Тест-аспект: пропуск сеттла невидим тестам байт-точности - чтение корректно,
а пропущенный pins.submit стреляет IMA только на первом decode на железе
(note-count ловушка). Контракт "on_done ровно один на задачу" проверять
явным тестом mixed-плана (zero-job + читающая) по списку событий, а не через
корректность чтения. Fails-before фикса был дословным: settled терял 'empty'
([../cases/boot-shutdown-io/P7-NOTES.md](../cases/boot-shutdown-io/P7-NOTES.md)).

## Сопутствующий урок волны P9: evidence-preserving error paths - cleanup запрещён после армирования

Многофазный транзакционный протокол (two-phase сжатия тир-блоба, волна P9:
blob.bin.new + journal.log.new -> swap.token -> hard-link .old якорей ->
rename -> unlink) кладёт на диск evidence фаз, по которому бут-рекавери
дошивает состояние. Ревью волны поймало два MAJOR-урока об error-путях:

- runtime-OSError в фазе коммита ПОСЛЕ армирования: except-блок НЕ имеет
  права чистить - unlink сносит .old якоря, синхронный откат становится
  невозможен, а рекавери теряет индикатор фазы (pre-fix сценарий стоил бы
  crc-дроп всех живых записей). Правило: после армирования откат - только
  синхронный через .old; невозможен - оставить ВСЁ бут-рекавери; unlink
  якорей/токена - строго после финального fsync_dir.
- повторный запуск операции при висящем армированном состоянии затирал
  evidence поверх разошедшегося диска. Гвард на входе: evidence есть ->
  warning + no-op (стор до рестарта живёт на mismatched in-memory офсетах -
  принятое следствие; бут сходится байт-в-байт).
- предикат rollback-vs-complete обязан опираться на индикатор фазы (якоря),
  а не на сравнение размеров: при совпадении старого и нового объёмов
  размеры неоднозначны; старые размеры в токене покрывают только фазу до
  якорей.

Тест-аспект: SIGKILL-матрица фазовых окон детерминированна без реальных
крэшей - monkeypatch os.link/os.rename/os.unlink/записи токена с unwrapped
исключением на каждой границе фаз, затем бут -> старое ИЛИ сжатое
состояние, живые записи бит-в-бит
([P9-NOTES.md](../cases/boot-shutdown-io/P9-NOTES.md)).

## Когда применять

- Любой тест многопоточного конвейера/пайплайна: события, не таймеры.
- Счётчик событий из рабочего потока: flush-локальный аккумулятор с одним
  писателем на поле и чтением после join, не общий `self._counters`.
- Любой инвариант "общее состояние меняется только под локом":
  source-привязка плюс поведенческий тест, не вместо него.
- План с no-op задачами и failable-бэкендом с fallback: сеттл после выбора
  исполнителя, контракт завершения - явным событийным тестом.
- Многофазный транзакционный протокол с армированием: except после
  армирования evidence не чистит (откат через якоря либо всё бут-рекавери),
  гвард повторного входа, матрица фазовых окон monkeypatch ос-примитивов.
