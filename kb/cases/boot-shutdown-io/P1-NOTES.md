# Волна P1: форма чтения загрузчика FTW-банков

Реализация брифа задачи P1 из [TASK.md](TASK.md) ("Задача P1"). Цель: поднять
среднюю скорость фазы загрузки банков с ~4.3 ГБ/с (125 ГиБ за 28-29 с; конфиг
измерения - раздел "Конфигурация всех измерений" [TASK.md](TASK.md)) до
>= 5.5 ГБ/с (фаза <= 23 с) без изменения пин-контракта. Волновой план вёлся в
git-игнорируемом рабочем каталоге кампании; все числа продублированы здесь.

## Механика: было -> стало

- **Было.** Каждый `read_into` открывал СВОЙ вложенный пул на 8 воркеров,
  внешний пул разворачивал до 16 задач -> вилка до 16x8 = 128 конкурентных
  чтений по 8 МиБ; суммарно до 9 пулов, пик 36 живых job'ов. Форма совпадает
  с провальной fio-точкой 16xQD8x8M = 4.70 ГБ/с
  ([TASK.md](TASK.md), "Формы чтения самого диска").
- **Стало.** Один ограниченный общий пул `_run_shared_reads`
  (ThreadPoolExecutor(8), глубина очереди ~QD16 по 1 МиБ эффективного
  параллелизма), sub-read `_BANK_SUB_CHUNK = 2 МиБ`. Форма приближена к
  fio-прецеденту 1xQD32x1M = 6.45 ГБ/с - лучшей измеренной форме этого диска.
- **Порядок задач layer-major:** задачи собираются по (layer_id, name), чтобы
  каждый воркер читал близкие регионы (меньше переключений внутри устройства);
  name-major оставлен как запасной вариант для железной руки.
- **on_done ровно один на банк:** прогресс и `pins.submit` вызываются через
  `add_done_callback` + счётчик завершённых sub-read'ов банка - контракт
  `tracker.note` (ровно один note на слой, иначе пиннинг молча пропускается)
  не тронут; ревью подтвердило чистоту по пин-контракту и байт-точности.
- **Контракт `read_into` не менялся:** `iter_ftw_weights` ходит через него,
  семантика внешних вызовов сохранена.

## База и цель (конфиг - железо 2026-09-27, [TASK.md](TASK.md))

| метрика | база | цель |
|---|---|---|
| фаза банков 125 ГиБ | 28-29 с | <= 23 с |
| средняя скорость фазы | ~4.3 ГБ/с | >= 5.5 ГБ/с |

Born-pinned (`FREETOKEN_BANK_CUDA_ALLOC=1`) опровергнут раньше рукой B
(32 с против 28-29 с) - рычагом не считается. Оценка выигрыша формы
(меньше потоков + глубже очередь): 1.4-1.5x; подтвердится только железной A/B.

## libaio/io_uring - открытый фоллоу-ап (не делать вслепую)

Системные библиотеки есть (`libaio.so.1t64`, `liburing.so.2`), python-обёрток
нет. Ctypes-путь реалистичен, но отложен за швом `_run_shared_reads` по двум
причинам:

1. фаза загрузки банков идёт параллельно со строительством CUDA-контекста -
   замена бэкенда затрагивает thread-safety этого окна;
2. любое perf-утверждение требует железной A/B, которую волна сделать не могла
   (VRAM занята локальным LLM).

Решение о ctypes-пути - отдельное (прецедент одобрения зависимости -
crc32c в [P3-NOTES.md](P3-NOTES.md)); пока backend=direct на системном пуле.
См. также [../../topics/ftw-load-path.md](../../topics/ftw-load-path.md).

## Наблюдаемость конфигурации (учат уроку - [../../methods/env-config-hygiene.md](../../methods/env-config-hygiene.md))

- Один вызов на бут: `FTW bank reads: N tasks, M jobs, pool=N, sub-chunk=KiB,
  backend=direct|mmap` - logger.info на уровне конфигурации пула; спам от
  `read_into` опровергнут на STOP GATE (один call-site).
- Clamp-warning: при `FREETOKEN_BANK_POOL_WORKERS` вне допустимого диапазона -
  предупреждение вместо тихого clamp'а. Без него железная A/B могла бы
  приписать результат не той конфигурации.

## Тесты (CPU-приёмка волны)

- `tests/checkpoint/test_ftw_bank_pool.py` 10/10; весь `tests/checkpoint`:
  33 passed + 6 skipped + 4 CUDA-environment errors = установленный базлайн
  этой машины (errors - не регресс: нет CUDA без VRAM).
- Fails-before: `git stash` правок прод-кода + md5-контроль файла до/после
  (метод - [../../methods/test-fails-before.md](../../methods/test-fails-before.md));
  на старом коде 7 тестов падали дословно. Старая форма доказана инвентаризацией:
  9 пулов / пик 36 job'ов против 1 пул / пик <= 8.
- Тайминг-гард в тестах ослаблен сознательно: абсолютные тайминги CPU-relative,
  реальные числа даст только железо (правило детерминированных таймингов).

## План железной руки (отложен, VRAM)

- A/B на том же стенде и флагах: фаза <= 23 с, средняя >= 5.5 ГБ/с.
- Свип `FREETOKEN_BANK_POOL_WORKERS` 4/6/8.
- Следить за syscall-оверхедом 2-МиБ sub-read (CPU-время фазы не должно расти),

  локальность.
