# Волна P3: параллельный флаш L2 + групповой fdatasync + CRC32C

Реализация брифа задачи P3 из [TASK.md](TASK.md). Цель волны: поднять пропускную
способность флаша L2 при остановке с измеренных ~200 МБ/с (плюс ~15 с
компакт-хвост; конфиг измерения - [TASK.md](TASK.md), "Задача P3") до
>= 1.5-2 ГБ/с на флаше ~9 ГиБ. Волна CPU-шная (локальный LLM занял VRAM), её
волновой план вёлся в git-игнорируемом рабочем каталоге кампании и после чистого
клона считается утраченным; все числа продублированы ниже.

## Что вошло в волну

- Параллельный флаш: резерв офсетов блоба заранее (`_reserve_blob_span`),
  запись сегментов группы параллельными pwrite-пачками (`_FLUSH_WRITERS = 8`,
  O_WRONLY-фд БЕЗ O_APPEND) вместо одного последовательного `os.write` в
  буферизованный O_APPEND-файл.
- Групповой fdatasync: сегменты батчатся в группы ~ `_FLUSH_GROUP_BYTES` = 1 ГиБ
  по объёму; ОДИН `os.fdatasync` делает группу durable перед журнальными
  записями этой группы (было: fsync блоба на каждый сегмент + fsync журнала на
  каждую запись).
- CRC32C-версионирование: payload-чек суммы журнала и блоба переведены на
  аппаратный CRC32C с per-record версией алгоритма.
- Попутно два реальных фикса и один блокер из ревью (раздел "Баги волны").

Механика пути: `flush_live` батчит живые L1-сегменты в группы по padded-объёму,
`_flush_group` заранее резервирует каждому сегменту span офсетов, пишет
параллельно, делает один fdatasync, затем пишет журнальные записи группы.
Односегментный runtime-путь (`_write_blob` при offer/evict-давлении) остался
прежним по структуре: резерв + pwrite + fdatasync + журнальная запись.

## Инвариант durable и окно потери

Инвариант сохранён: журнальная запись появляется только после того, как байты
блоба её группы durable. Ценой параллелизации стало окно потери: SIGKILL между
fdatasync группы и её журнальными аппендами оставляет durable-хвост блоба без
журнальных записей - реплей отбрасывает его (конвергенция прежняя: сегменты
остаются в L1 в выжившем процессе). Окно расширено с одного сегмента до целой
группы ~1 ГиБ; задокументировано в докстринге `_flush_group`. Каждая ошибка
записи возвращает False: ни журнальной записи, ни учёта ёмкости ("no journal
entry, no capacity accounting").

## Watermark вместо lseek (дыры от pwrite)

Параллельная запись по зарезервированным офсетам порождает дыры: провал одной
pwrite оставляет незаписанный промежуток за watermark-ом блоба. Ревью-кандидат
"подрезать watermark к фактическому концу" отклонён (FP-триаж): подрезка
гоняется с writer'ами и ломает контракт never-decreased eof. Проверено, что дыры
безопасны как есть: маркер чистой остановки из волны P2 пишет реальный
`getsize` файла, поэтому fast-path реплея принимается корректно - дыры за
watermark-ом журналом не референсируются. Тест-защита (переименован волной):
`test_short_blob_pwrite_hole_kept_watermark_past_it_next_record_clean`.

## CRC32C: выбор пакета и совместимость

- isal НЕ экспонирует CRC32C: в библиотеке только IEEE-вариант, эквивалентный
  `zlib.crc32`; попытка дотянуться до скрытого C-символа CRC32C через ctypes
  падает segfault-ом (замерено зондом в волне). Выбран пакет `crc32c`
  (pyproject: `crc32c>=2.9,<3`, одобрение пользователя).
- Версионирование per-record: новая запись несёт `"crc_alg":"crc32c"`,
  ОТСУТСТВИЕ поля = zlib (старые директории продолжают проверяться старым
  алгоритмом - обязательная совместимость соблюдена).
- Обрамление журнала осталось zlib: алгоритм CRC записи нельзя узнать, пока
  запись не разобрана (курица-яйцо), а zlib на журнальных заголовках стоит
  килобайты против гибибайт payload.
- Даунгрейд: старый бинарник на новом каталоге отбрасывает crc32c-записи как
  dead - журнал остаётся well-formed, директория не крошится.
- Аппаратный CRC32C ускоряет не только запись, но и краш-путь полной верификации
  реплея из [P2-NOTES.md](P2-NOTES.md) (там же конфиг базового числа ~1.9 ГБ/с
  на zlib.crc32).

## Баги волны

1. **Stale journal fd после компакции - пре-существующий HEAD-баг (самое
   важное).** Введён коммитом runtime-компакции 2348da5 и присутствовал на базе
   волны 621d100. Механика: `compact()` переписывает журнал (сбрасывая dead
   записи) и замещает файл, но журнальный fd не переоткрывался - аппенды после
   компакции уходили в отлинкованный inode. Итог: молчаливая потеря ВСЕГО
   пост-компактного флаша при ребуте (журнальные записи писались в файл,
   которого больше нет). Фикс: переоткрытие `_journal_fd` после перезаписи
   журнала в `compact()`. Поймал первый тест с маршрутом flush -> compact ->
   offer -> boot: первый аппенд ПОСЛЕ компакции, сбросившей записи, идёт через
   границу бута - реплей не видит записей, которые журнал формально "писал".
2. **Cap-регрессия группового резерва** (регресс самого диффа волны): резерв
   офсетов группы не учитывал pending-байты уже зарезервированных сегментов
   группы в cap-чеке, использованное могло уйти за кэп до размера группы (~1 ГиБ).
   Фикс: строгий кэп в `_reserve_blob_span(need, pending)` с суммой группы;
   fails-before эмпирический - до фикса тест фиксировал 8 ГиБ при кэпе 4 ГиБ
   (assert 8 == 4).
3. **Dict-mutation mid-iteration в `flush_live`** (BLOCKER ревью A, регресс
   диффа): mid-loop cap-eviction (`_flush_group` -> `_reserve_blob_span` ->
   `_evict_oldest_l2` -> `_discard`) удалял из `_segments` прямо во время
   итерации. Фикс: снапшот `list(self._segments.values())`.

## Тест-уроки волны

- **fails-before эмпирический через точечный реверт.** HEAD к началу волны уже
  далеко ушёл от пре-фиксного состояния (пре-существующий баг и правки соседних
  волн), поэтому stash-приём из [test-fails-before.md](../../methods/test-fails-before.md)
  недоступен напрямую. Новизна регрессионных тестов доказывалась точечным
  ревертом конкретных TP-правок волны из рабочего дерева: реверт правки ->
  прогон (тест красный) -> возврат правки. Для пре-существующего stale-fd это
  единственный способ показать красный ДО, не откатывая чужие волны.
- **Тест-маршрут важнее утверждения.** Тест flush -> compact -> offer -> boot
  поймал stale-fd именно потому, что маршрутом задал первый аппенд после
  компакции, сбросившей записи, через границу бута; более короткие маршруты
  (без компакции или без перезапуска) бага не видят.
- Battery: 62/62 (`tests/scheduler/test_session_tier.py`) + 70/70
  (test_hybrid_cache_manager), независимый прогон зелёный; faulthandler-транзиент
  первого прогона классифицирован Environment (два повторных прогона чистые).

## Замеренный контекст и незакрытое

- База мотивации (железо 2026-09-28, флаги оператора в [TASK.md](TASK.md)):
  флаш ~200 МБ/с плюс ~15 с компакт-хвост в стопе. Цель >= 1.5-2 ГБ/с на ~9 ГиБ
  НЕ проверена - железная рука отложена (нужна VRAM, локальный LLM резидентен).
- Железная рука, когда VRAM освободится: реальный флаш ~9 ГиБ (наполнить L1
  длинными диалогами, group-SIGTERM с grace 180) -> iostat >= 1.5-2 ГБ/с;
  восстановление байт-в-байт и resume HIT; SIGKILL между группами;
  SIGKILL-после-компакции (проверка stale-fd фикса); A/B числа воркеров.
- Блокер железной A/B: у `_FLUSH_WRITERS` / `_FLUSH_GROUP_BYTES` пока нет
  env/config-override - нужен follow-up PR, иначе A/B по числу воркеров не
  поставить. Прочие follow-up: деталь abort-лога группы, метрики группы в
  snapshot/stats_line.
- Коммит волны (session_tier.py + pyproject.toml + тесты) - решение пользователя
  на STOP GATE; kb-дистилляция выполняется до коммита.
