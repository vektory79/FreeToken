# Волна P5-минимум: overflow-наблюдаемость LRU-эвикций shutdown-флаша

Бриф - задача P5 из [TASK.md](TASK.md): graceful-стоп при used > кэпа
исторически стирал живое L2. Итог волны: семантику вытеснения менять не стали
(решение пользователя - P5-минимум), добавили наблюдаемость переполнения кэпа.

## Решение пользователя

Из трёх опций спецификации выбран P5-минимум: LRU-admission остаётся как есть,
добавляется лог/счётчик эвикций на стопе; опция (б) "кэп - только runtime-гейт"
(неограниченный рост блоба, но ничего не стирается) не делалась; wipe-опция (в)
не потребовалась - см. корень исторического wipe ниже.

## Исследование перед кодом: LRU уже в проде

- Runtime-пути вытеснения и стоп-флаш выбирают одну и ту же жертву: min по
  (last_validation, seg_id) (`_evict_oldest_l2`, строки рабочего дерева
  session_tier.py :1086-1091; runtime-пути - тот же ключ). last_validation -
  настоящая валюта LRU: её освежают restore, consume_ticket и матч снапшотов;
  бут восстанавливает штампы из ts журнала.
- Стоп-флаш резервирует span блоба через `_reserve_blob_span` (:751), который
  при исчерпании кэпа вызывает эвикцию с учётом pending (:765): жертвуется
  ровно столько старого L2, сколько нужно флашу, - не весь кэп.
- Отказ "L2 cap reached, cannot demote" сегодня достижим, только если одна
  группа не влезает в кэп даже после полной эвикции L2: при кэпе 60 ГиБ и
  группах 1-2 ГиБ (дефолт P4/P6) - недостижимо.
- Исторический wipe (discard всех записей + truncate блоба до 0 за 0.6-2 с,
  наблюдения ARM2 приёмки P2 и P3-iron) был вырождением бага cap-accounting
  fast-бута: `_ssd_used` сеялся размером блоба (водяной знак с dead-спанами),
  эвикции его не снижали -> все demote REFUSED -> компакт с пустым keep
  обтрунцивал блоб. Корень закрыт фикс ab3a117 (пересев из живой суммы на
  обоих путях бута); после него admission стал dead-независимым, то есть
  детерминированным.

## Реализация: flush-локальный талли и одна лог-строка

- `_FlushOverflow` (session_tier.py :209, рабочее дерево) - талли одной фазы
  `flush_live`: records (вытеснено записей L2), bytes (освобождённый
  padded-span), admitted (журналированные байты флаша - это Y в логе).
- Талли живёт в слоте `self._flush_overflow` (:431), ставится и сбрасывается
  try/finally вокруг `_flush_groups` (:1437-1441); на runtime-путях слот None.
- Аккумуляция намеренно НЕ в `self._counters` (урок P4 о shared-счётчиках):
  билдер-поток считает эвикции вне стора-лока, поэтому у объекта один писатель
  на поле (билдер - records/bytes, поток флаша - admitted), а `flush_live`
  читает сумму только после join билдера. Ни одного лока на горячем пути;
  методическая запись -
  [deterministic-concurrency-tests.md](../../methods/deterministic-concurrency-tests.md).
- Лог - одна строка на фазу флаша и только при эвикциях (:1445):
  "session tier: flush overflow: evicted N records / X.X MiB of oldest L2 to
  admit Y bytes"; без эвикций - тишина (строка "flushed N live segments"
  осталась без изменений).

## Тесты

- Три новых в `tests/scheduler/test_session_tier.py` (маркер раздела
  "P5 flush overflow observability"): ровно одна overflow-строка при
  cap-эвикциях резерва; тишина при флаше без эвикций; drain-retry эвикция
  (отказ резерва с пустой группой, затем жертва) попадает в тот же талли -
  отказ-первый порядок форсируется детерминированно, событиями.
- Батарея: 82/82 `test_session_tier.py` (3 новых) + 70/70
  `test_hybrid_cache_manager` (CPU pytest, без VRAM).

## Тайминг-контекст over-cap стопа (исследование волны)

Конфиг: флаги оператора ([TASK.md](TASK.md), "Конфигурация всех измерений"),
L2-кэп 60 ГиБ, live L2 51.03 GiB, blob 132.4 GB (постфлайт железной приёмки
P4, [P4-NOTES.md](P4-NOTES.md)).

- Эвикция при over-cap - ~0 с: жертва выбирается и отбрасывается в памяти,
  без fsync; сотни эвикций - < 0.1 с (исследование на CPU).
- Доминанта стопа - компакт: на graceful-стопе он вызывается безусловно
  (shutdown-путь cache.py) и при dead > 0 копирует выжившие live-спаны QD1
  (0.6-1 ГБ/с на этом NVMe). Оценка для прода: 55-90 с при live 51 GiB
  (замерный якорь масштаба: ~15 с хвост компакта на P3-iron при
  live ~10-15 ГБ).
- Прода это касается уже сейчас: blob 132.4 GB при live 51.03 GiB даёт
  dead ~60% блоба; порог maybe_compact (25% dead) давно превышен.
  Прогноз "очередной runtime-оффер сам даст паузу" опровергнут железом
  2026-09-30: офферные compact() но-оп при 0 мёртвых записей (см.
  "Железная рука" ниже). Компакт в P4/P5 не ускорялся - кандидат на
  отдельный рычаг.
- Опция (б) дала бы 0 эвикций -> 0 dead -> компакт но-оп (чистый флаш
  4.1-4.7 с по P4-iron при 2.18-2.46 ГБ/с) ценой неограниченного роста блоба -
  отклонена в том числе из-за уже раздутых 132.4 GB.
- Бут после LRU-стопа: маркер чистой остановки валиден -> fast-path ~0 с
  (P2); после SIGKILL - полный реплей с CRC-перечиткой (оценка ~27 с при
  live 51 GiB); dead-байты пересеиваются точно (фикс ab3a117).

## Железная рука (2026-09-30): все гейты приняты

Код под тестом - P5-минимум, закоммиченный 94e4783 (P4 b99a103
+ P6 dd349a6 закоммичены); артефакты - `.tasks/boot-shutdown-io/p5-iron/`
(вне git, после клона считаются утраченными; все числа продублированы
текстом ниже). Методика over-cap: кэп опущен флагом оператора
`--session-tier-ssd-gib 45` при live 51.03 GiB - одна серия fill вместо
2-3: объём флаша идентичен P4-железу (9.83 GiB / 52 сегмента, прямое
сравнение темпов), гейт ">= 20% поверх кэпа" взят с запасом (would-be
60.86 GiB = 135% от 45), при 2+ сериях L1-давление рождает тихие
runtime-эвикции вне талли. Путь тот же, что в проде: `_reserve_blob_span`
-> `_evict_oldest_l2` (LRU как есть).

| гейт | результат |
|---|---|
| PHASE-0: dead прода | 72.29 GiB = 58.6% от blob 132.4 GB (270 records, live 51.03; ожидание ~60% совпало) |
| over-cap стоп (L2 >= 20% поверх кэпа) | принят: would-be 60.86 GiB против кэпа 45 = 135% |
| overflow-строка прод-масштаба | принята: 84 records / 16257.9 MiB, admit 10553254400 B |
| арифметика LRU бит-в-бит | принята: 238 = 270-84+52 records; 44.98 = 51.03-15.88+9.83 GiB |
| byte-exact / resume HIT | принят: 5/5 выживших cached 9280/9324 (99.5%); эвикнутый - MISS |
| бут после LRU-стопа | принят: fast-path 0 с (цель <= 2 с), 238 records, used= 44.98 GiB |
| инцидент wipe/truncate | нет: 0 refusals/truncate/torn; маркер VALID gen 3->4 |
| постфлайт | VRAM 1152 MiB; сервер/вотчеры не текут; дерево бит-в-бит |

SIGKILL-рука брифа (часть гейта 4) на over-cap стопе отдельно не гонялась:
краш-конвергенция конвейера флаша уже доказана P4-железом; P5-рука
сфокусирована на graceful-стопе.

### Тайминги over-cap стопа

Стоп SIGTERM группе, grace 300 с (backstop не понадобился); замеры:
blob-кривая 20 Гц (вкл. blob.bin.compact), /proc/diskstats 10 Гц.

| фаза | t (от SIGTERM) | объём | темп | util диска |
|---|---|---|---|---|
| флаш (writers=8, группы 1 GiB) | 3.62 с | 9.805 GiB | 2.91 ГБ/с (blob) / 2.23 ГБ/с (device) | 44% |
| эвикции 84 records | ~0 с (in-memory, внутри окна флаша) | 16257.9 MiB | - | - |
| компакт (shutdown, после флаша) | 81.3 с | 44.98 GiB live переписан | 0.57 ГиБ/с (0.60 ГБ/с device, QD1) | 86% |
| полный стоп (SIGTERM -> exit) | 98 с | 54.82 GiB записано на диск | - | 15% среднее |

- Эвикции бесплатны: 3.62 с / 2.91 ГБ/с против 2.18-2.46 ГБ/с P4-железа
  на том же объёме БЕЗ эвикций - паритет/лучше; прогноз "< 0.1 с на сотни
  эвикций" подтверждён.
- Компакт - доминанта стопа (81.3 из 98 с = 83%): оценка брифа 55-90 с
  попала; темп 0.60 ГБ/с QD1 при util 86% - кандидат на ускорение
  (открытые кандидаты ниже).

### LRU-симметрия и бут

- Бут после стопа: fast-path 0 с ("replay fast-path (clean shutdown
  marker), 238 records"), used= 44.98 GiB бит-в-бит, 0 dropped/torn.
- 5/5 выживших (2 старых P4-волны + 3 новых) HIT: cached=9280 одинаковый
  бит-в-бит (99.5%); эвикнутая старейшая (P3-эра) - MISS с полным
  репрефиллом 14.5 с. Все 5 хитов восстановлены именно из L2 (restore=5).
- Overflow-строка прод-масштаба: "session tier: flush overflow: evicted
  84 records / 16257.9 MiB of oldest L2 to admit 10553254400 bytes";
  в финальном стопе БЕЗ кап-давления (кэп 60, live 45.4) - тишина.
- Эвикнутые - старейшие тест-волны (P2/P3 fill), не операторские сессии;
  "НЕТ стирания всего": truncate нет, 238 records живы.

### Открытые кандидаты (находки вне гейтов)

1. Watermark maybe_compact vs record-based no-op: бут сеит `_dead_bytes`
   физическими дырами (blob_eof - live), но `compact()` но-оп при 0 мёртвых
   ЗАПИСЕЙ (все 270 записей журнала живы - дыры остались от прежних
   поколений/компактов). Итог: watermark вечно "просрочен" (72-88 GiB >
   порога 25%), каждый ok-оффер платит полный `_parse_journal` впустую;
   финальная строка стопа "dead=90284 MiB" при нулевой работе компакта
   дезинформирует. Кандидат: гейтить compact() по числу мёртвых записей
   либо пересеивать watermark от record-identity.
2. Файл никогда не сжимается: компакт копирует live-спаны НА ИХ ОФСЕТЫ -
   после компакта blob 133.15 GiB при live 44.98 GiB (физически dead
   88.17 GiB = 66% сохраняется), `_dead_bytes` = 0. Реальное сжатие
   (полная перезапись с новыми офсетами) - отдельный рычаг.
3. Темп компакта 0.60 ГБ/с QD1 при util 86% - доминанта стопа; ускорение
   копирующего потока - отдельный рычаг.
