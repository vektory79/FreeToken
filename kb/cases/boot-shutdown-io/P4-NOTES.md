# Волна P4: zero-copy pwritev из L1-пула + конвейер групп флаша

Реализация брифа задачи P4 из [TASK.md](TASK.md). Цель волны: устранить
продюсер-узкое место флаша L2, измеренное железной приёмкой P3
([P3-NOTES.md](P3-NOTES.md)): 0.93-1.16 ГБ/с при утилизации NVMe 20-40% на
байт-идентичном флаше 9.83 ГиБ / 52 сегмента (флаги оператора -
[TASK.md](TASK.md), "Конфигурация всех измерений"). Целевые числа не
перепроверялись - железная рука отложена (VRAM; пре-реквизит - env-override
`_FLUSH_WRITERS`/`_FLUSH_GROUP_BYTES`, задача P6). Волновой план:
`.tasks/boot-shutdown-io/p4-plan/PLAN.md` (вне git, после клона считается
утраченным).

## Механика записи: zero-copy pwritev из регионов L1-пула

- Страницы сегмента в L1-пуле НЕ смежны (дедуп страниц и refcount дают
  разрывную раскладку) - смежных регионов пул не экспонирует. Смежность и
  не нужна: набор iovecs `pwritev` покрывает разрозненные страницы без
  копий. Сборка единого payload (постраничные `bytearray`-копии из брифа
  P3) устранена полностью.
- Срезы пула берутся `memoryview`-чанками по `pool.mm`; pwritev идёт
  чанками до 512 iov (лимит ядра на `IOV_MAX`; для больших сегментов -
  последовательность pwritev по зарезервированному span).
- Выравнивание хвостов - pad из статического `_ZERO_BLK`, а не аллокация
  на месте: байт-идентичность блоба относительно сборки payload сохранена
  (нулевые страницы остаются нулевыми байтами).
- CRC32C по payload - цепочечный по need-байтам поверх тех же iovecs:
  пакет `crc32c` освобождает GIL с ~32 КиБ входа, поэтому crc билдера
  перекрывается с записью консьюмера. Журнальные записи группы - один
  аппенд после fdatasync группы.
- Односегментный runtime-путь `_write_blob` (offer/evict-давление) НЕ
  тронут - конвейер живёт только в shutdown-флаш (`flush_live`).

## Конвейер групп (double buffering)

- `flush_live` собирает ВСЕ группы списком ДО старта конвейера: коллекция
  и флаш разделены, мутирования словаря сегментов во время флаша больше
  нет (урок P3 о dict-mutation закреплён структурой, а не снапшотом).
- `_flush_groups`: билдер-поток (`ThreadPoolExecutor(1)`) строит группу
  N+1 (резерв span + iovecs + CRC), консьюмер (main) пишет группу N
  (pwritev -> ОДИН fdatasync -> журнальные записи группы).
- Инвариант неприкосновенен: журнальная запись появляется только после
  durable блоба своей группы. Окно потери при краше НЕ расширено -
  по-прежнему "группа" (~`_FLUSH_GROUP_BYTES`), не весь флаш.
- Захват/высвобождение ресурсов группы (`_GroupEntry`): pending-объём,
  refs страниц, stage. Идёмпотентность обеспечивает флаг `_GroupEntry.released`.

## Синхронизация: почему три примитива, а не один лок

- `_PendingVolume` (Condition) - pending-объём ещё НЕ журналированных
  групп: add делает билдер на резерве, release - консьюмер в `finally`.
  Это то, что cap-чек `_reserve_blob_span` вычитает из кэпа (семантика
  pending из волны P3).
- `_account_lock` - нереентрантный leaf-lock вокруг `_ssd_used` /
  `_dead_bytes`. Leaf-lock принципиально: обкладывать локом evictor
  нельзя - это само-дедлок на нереентрантном локе; незалоченный
  снапшот в cap-чеке консервативен (может отказать лишний раз, не может
  переполнить). Дополнительный `_account_lock` в cap-чек НЕ добавлялся -
  обоснование зафиксировано в коде.
- Правило "билдер не берёт `_lock`" (глобальный RLock): писатель держит
  его на протяжении группы - билдер, взявший бы `_lock`, дедлокнулся бы.
  Всё, что билдеру нужно (резерв, аккаунтинг), идёт через leaf-lock.

## P3-семантика жертвы восстановлена (drain-retry)

При отказе резерва (cap-чек) с пустым stage билдер НЕ падает и НЕ пишет
мимо кэпа: ждёт drain pending (граница 60 с с warning) и повторяет
резерв. Граница bounded - не бесконечное ожидание. Fallback после
таймаута: резерв с pending=0 может временно перекрыть кэп на объём
группы (~1 ГиБ) - допустимо только на shutdown-флаше, задокументировано
в коде.

## BaseException-безопасность

`_release_stage` (идемпотентный флаг `released`) высвобождает pending +
refs на всех трёх путях: `finally` писателя, `except` билдера, свип
необработанных групп в `_flush_groups`. `KeyboardInterrupt` пробрасывается
как KI (не глушится `except Exception`-подобными обёртками) - тест на
это есть.

- Лог отказа билдера называет group index, seg_id и байты - отказ

  pending=0 в логе стопа.

## Замеренный контекст и незакрытое

- База: P3-флаш 0.93-1.16 ГБ/с (iostat / blob-кривая) при утилизации
  диска 20-40% - узкое место продюсер (флаги и стенд - [P3-NOTES.md](P3-NOTES.md),
  раздел "Железная приёмка"; там же методика воспроизведения).
- Цель P4 (>= 1.5-2 ГБ/с, util >= 60%) НЕ перепроверялась - железная
  рука отложена: нужна VRAM и env-override `_FLUSH_WRITERS` /
  `_FLUSH_GROUP_BYTES` (задача P6, пре-реквизит; план руки - в брифе P4
  [TASK.md](TASK.md) и wave log в `.tasks/boot-shutdown-io/p4-plan/PLAN.md`).
- Коммит волны не сделан (решение пользователя); до коммита правки
  session_tier.py и тестов лежат в рабочем дереве vektory79 @ 5f9abcc.
