# Старт и остановка ft serve: три узких места I/O (измерено, брифы фиксов)

**Вердикт (читать первым).** Три жалобы оператора на старт/остановку конфигурации
GLM-5.3-Flash GGUF FTW (гибрид, tier 10/50 GiB) проверены железом 2026-09-27;

1. Загрузка MoE-банков (125 ГиБ за 28-29 с, средняя ~4.3 ГБ/с) упирается в
   многопоточную ФОРМУ чтения самого NVMe: 16 параллельных потоков дают
   4.7-4.9 ГБ/с против 6.45 ГБ/с у одного потока с очередью 32. Пиннинг-конвейер
   опровергнут A/B-рукой (born-pinned не быстрее). Рычаг: меньше потоков, глубже
   очередь на каждый -> ~1.4-1.5x на фазе (задача P1).
2. Медленная "загрузка L2" на буте - это `replay_journal` с полной CRC-перечиткой
   всего блоба: 22-24 с на каждом буте при 41.41 ГиБ живого L2. После graceful-
   остановки проверка избыточна. Рычаг: маркер чистой остановки -> минус ~22 с
   с каждого старта (задача P2).
3. Флаш в L2 при остановке (200-400 МБ/с у оператора) - это чистый путь записи:
   строго последовательные сегменты, fsync на каждый сегмент и на каждую
   журнальную запись, всё под глобальным локом; компакт у этого кеша не участвует
   (dead = 0). Рычаги: параллельная запись с групповым fsync + аппаратный CRC32C
   + сокращение объёма дедупом (задача P3).

# Задача P1: форма чтения загрузчика FTW-банков

**Цель.** Поднять среднюю скорость фазы загрузки банков с ~4.3 до >= 5.5 ГБ/с
(фаза <= 23 с) без изменения пин-контракта и без регресса бута.

**Якоря (655da16).** `python/freetoken/checkpoint/ftw.py`: константа
`_DEFAULT_CHUNK` (8 МиБ) и `_BANK_CONCURRENCY = 4` (внешний пул разворачивается
в 16 задач), `read_into` на каждую задачу открывает СВОЙ вложенный пул на
8 воркеров -> до 128 параллельных чтений; `load_ftw_banks` собирает задачи
per (bank, layer) и подчиняет их пулу минимум в 16 потоков.

**Спецификация.** Один общий ограниченный пул чтения (4-8 воркеров) с глубокой
очередью на поток (QD 8-16) вместо вилки 16 x 8; предпочтительно io_uring/libaio
(прецедент замера: fio 1xQD32x1M = 6.45 ГБ/с). Порядок задач - по слойм, чтобы
потоки читали близкие регионы (меньше переключений потоков внутри устройства).
Born-pinned (`FREETOKEN_BANK_CUDA_ALLOC`) рычагом НЕ считать - опровергнут
рукой B; `born_pinned_default` и пин-контракт (`tracker.note` ровно один на
слой, иначе пиннинг молча пропускается) не трогать.

**Приёмка.** A/B на этом же стенде и флагах: фаза банков <= 23 с и средняя
>= 5.5 ГБ/с; регресс-тесты пин-контракта зелёные; батарея качества бута в
паритете; CPU-время фазы не растёт.

**Железная приёмка (2026-09-29/30): принято частично.** Реализовано и
закоммичено (94d5e4a, ftw.py + тесты test_ftw_bank_pool.py, fails-before
эмпирический). Пять бутов на флагах оператора, фаза = бар "Loading expert
banks (FTW)", 125 ГиБ: база 23b18a4 = 28 с / 4.46 ГБ/с при CPU фазы 77.5 с
(sys 76.4); новый код pool=4 = 25 с / 5.00 ГБ/с (повтор бит-в-бит),
pool=6/8 = 26 с / 4.81; CPU фазы 32.6-40.6 с (sys 32.6-39.5). Гейт фазы
(<= 23 с / >= 5.5 ГБ/с) НЕ ПРОЙДЕН: 1.12x вместо 1.4-1.5x; свип пула
плоский - размер пула исчерпан как рычаг. CPU-гейт ПРОЙДЕН: sys-время
2.3x меньше (2-МиБ sub-read дешевле по syscall). Всплески 8-12.7 ГБ/с
в хвостах бара - лимитит пайплайн (глубина очереди), не устройство;
следующий рычаг - ctypes io_uring/libaio за швом `_run_shared_reads`
или оверлап пин-конвейера; гипотеза очереди проверена волной P7 и
ОПРОВЕРГНУТА (открыт только оверлап) -
[P7-NOTES.md](P7-NOTES.md). Таблица пяти рук, находка про
условную residency-строку и iostat-ловушку - [P1-NOTES.md](P1-NOTES.md).

# Задача P2: маркер чистой остановки -> быстрый реплей L2

**Цель.** Убрать полную CRC-перечитку блоба из бута после graceful-остановки:
реплей <= 2 с при 41 GiB живого L2 (сейчас 22-24 с на каждом буте).

**Якоря (655da16).** `python/freetoken/scheduler/session_tier.py`:
`replay_journal` (:949) для КАЖДОЙ записи читает весь payload и считает
`zlib.crc32(os.pread(...))` (:984) - однопоточно, буферизованный QD1 (~1.5 ГБ/с
потолок, см. комментарий `_blob_read`), crc держит GIL (~1-1.5 ГБ/с на ядро).
Проверка нужна только для сходимости после краха (дырки от прерванного
компакта, torn-хвост). Порядок durable задан в `_write_blob` (:547-585): блоб +
fsync ДО журнальной записи. Вызов на буте: `cache.py:293` из `CacheManager`.

**Спецификация.** После успешного завершения `shutdown_tier` (флаш + компакт +
fsync) писать барьер: fsync-нутую маркер-запись в журнал либо sidecar-файл с
размером журнала, eof блоба и поколением. На буте: маркер валиден (размеры
совпали, хвост журнала не порван) -> пропустить per-record CRC-перечитку,
только разобрать журнал; маркера нет или хвост torn -> полная верификация как
сейчас. Не трогать: порядок блоб-до-журнала, ключ выживания записей компакта
(path_key, off, n), отчёт "replay dropped N dead/torn records" для краш-пути.
В лог добавить явную строку fast-path ("session tier: replay fast-path (clean
shutdown marker), N records").

**Приёмка.** CPU-тесты (fail-before): clean-маркер даёт fast-path и не теряет
битые записи при симуляции краха; SIGKILL-рука на железе (прервать флаш или
компакт) -> маркера нет, полная верификация, конвергенция к живым сегментам;
железная рука: бут после graceful-стопа с 41 GiB L2 - реплей <= 2 с, resume
HIT без деградации.

**Ход волны.** Реализовано и закоммичено в vektory79 (621d100, коммит
"perf(scheduler): skip l2 blob crc re-read on boot via clean-shutdown
marker"): session_tier.py + cache.py + тесты + kb-дистилляция. CPU-прогон
46/46 и 70/70 зелёный, fails-before эмпирический. Механизм, инвалидация,
test-уроки: [P2-NOTES.md](P2-NOTES.md).

**Железная приёмка (2026-09-28): принято.** 9 бутов на флагах оператора
(порт 18821). ARM1 graceful: полный путь 22 с (112 записей / 80.23 GiB,
база 22-24 с совпала), fast-path буты 0 с при цели <= 2 с, маркер VALID
после каждого стопа, resume HIT (cached_tokens 9536/9582). ARM2 SIGKILL:
после перенастройки на evidence-триггер kill на t=+0.7 с посреди флаша ->
маркер ABSENT, бут по полному пути восстановил ровно журналированное
подмножество (1 запись, used 0.19 GiB, нежурналированный хвост блоба
проигнорирован), конвергенция к fast-path идентична. Полные таблицы и
разбор инцидентов - [P2-NOTES.md](P2-NOTES.md).

# Задача P3: путь записи флаша L2 (параллель + групповой fsync)

**Цель.** Поднять пропускную способность флаша с ~0.2-0.6 ГБ/с (якоря: ~600
МБ/с в [ft-serve-shutdown-signals.md](../../topics/ft-serve-shutdown-signals.md),
200-400 МБ/с у оператора) до >= 1.5-2 ГБ/с на флаше ~9 ГиБ.

**Якоря (655da16).** `session_tier.py`: `_demote`/`_write_blob` (:530-585) -
сборка payload постраничными копиями, один последовательный `os.write` в
БУФЕРИЗОВАННЫЙ O_APPEND-файл, `os.fsync` блоба на КАЖДЫЙ сегмент (:568), затем
`_journal_append` (:926-945) - JSON + crc + write + ещё один fsync на каждую
запись; `flush_live` (:916) держит глобальный RLock на весь цикл. Компакт
(:1043-1080) у рабочего кеша оператора не участвует (dead = 0) - тратить
усилия на него не нужно.

**Спецификация.** Заранее резервировать офсеты (`_blob_eof` += padded на
сегмент) и писать сегменты параллельно (4-8 воркеров, `pwrite` по
зарезервированным офсетам через O_WRONLY fd без O_APPEND; лучше - `pwritev`
прямо из регионов L1-пула, убрав сборку единого payload). Вместо fsync на
каждый сегмент - групповой fdatasync (группа по объёму, 1-2 ГиБ) перед
журнальными записями той группы; инвариант сохранить: журнальная запись
появляется только после durable блоба своей группы (окно потери при краше
расширяется с сегмента до группы - задокументировать). CRC payload и журнала
перевести на аппаратный CRC32C (isal/crc32c; `zlib.crc32` держит GIL и даёт
1-1.5 ГБ/с на ядро) - ускоряет и запись, и краш-путь реплея из P2. Опционально
флагом - сжатие payload (zstd на простаивающих при остановке ядрах), но сначала
померить коэффициент на fp32 GDN-снапшотах. Отдельный структурный рычаг объёма
- дедуп снапшот-сегментов L2: дизайн-решение описано в
[session-cache-tiering.md](../../topics/session-cache-tiering.md) (раздел
"Открытый вопрос"; дизайн-бриф лежит вне git и после клона считается
утраченным).

**Приёмка.** Железная рука с реальным флашем ~9 ГиБ (наполнить L1 длинными
диалогами, остановить group-SIGTERM с grace 180): пропускная способность флаша
>= 1.5-2 ГБ/с по iostat; восстановление после рестарта байт-в-байт и resume
HIT; CPU-тесты конвергенции реплея (в т.ч. SIGKILL между группами) зелёные;
окно потери задокументировано в докстринге.

**Ход волны (CPU, 2026-09-29).** Реализовано и закоммичено в vektory79
(de26ba1 "perf(scheduler): parallel l2 flush with group fdatasync and
crc32c": session_tier.py, pyproject.toml c `crc32c>=2.9,<3`, тесты):
параллельный pwrite-флаш
(8 воркеров, резерв офсетов), групповой fdatasync групп ~1 ГиБ перед
журнальными записями группы, CRC32C-версионирование per-record. Попутно два
реальных фикса: пре-существующий HEAD-баг stale journal fd после компакции
(введён 2348da5: аппенды после компакции уходили в отлинкованный inode -
молчаливая потеря всего пост-компактного флаша при ребуте) и cap-регрессия
группового резерва. CPU-гейт 62/62 + 70/70, fails-before эмпирический.
Механика, окно потери и тест-уроки: [P3-NOTES.md](P3-NOTES.md).

**Железная приёмка (2026-09-29): принято функционально, throughput-цель не
достигнута.** A/B на идентичном флаше 9.83 ГиБ / 52 сегмента: de26ba1 =
0.93 ГБ/с (iostat) / 1.16 ГБ/с (blob-кривая), база 621d100 = 0.65/0.63 -
ускорение ~1.4-1.8x; цель >= 1.5-2 ГБ/с НЕ достигнута: утилизация диска

fdatasync), не NVMe. Функциональные гейты PASS: resume HIT 9280/9325

от размера блоба (session_tier.py:329) вместо живой суммы - открытый вопрос

`_FLUSH_WRITERS`/`_FLUSH_GROUP_BYTES` (follow-up PR, задача P6 ниже).

# Задача P4: продюсер флаша L2 (throughput)

**Цель.** Поднять пропускную способность флаша с 0.93-1.16 ГБ/с (измерено на
de26ba1) до >= 1.5-2 ГБ/с на флаше ~9-10 ГиБ и утилизацию NVMe с 20-40% до
>= 60-70%. Узкое место установлен железной A/B (9.83 ГиБ / 52 сегмента,
байт-идентичный флаш): не диск, а продюсер - последовательная сборка payload
постраничными копиями из L1-пула и сериализованный групповой fdatasync
(следующая группа ждёт fdatasync предыдущей).

**Якоря (de26ba1).** `session_tier.py`: `_flush_group` (сборка ->
`_pwrite_span` -> fdatasync -> журнал группы), `_pwrite_span`, `flush_live`
(группы обрабатываются последовательно), константы `_FLUSH_GROUP_BYTES`
(1 ГиБ) и `_FLUSH_WRITERS` (8) - захардкожены, `_reserve_blob_span`
(pending-учёт кэпа).

**Спецификация.** (1) Параллельная сборка payload либо прямая запись без
сборки: `pwritev` прямо из регионов L1-пула (прецедент брифа P3); проверить,
экспонирует ли пул смежные регионы. (2) Конвейер групп: сборка группы N+1
параллельно с записью/fdatasync группы N (double buffering). Инвариант
неприкосновенен: журнальная запись группы только после durable блоба своей
группы; окно потери не расширять (сейчас - группа). (3) Тюнинг числа
воркеров/размера группы - через env-override (задача P6, пре-реквизит
железной руки). (4) Замер: blob-кривая и iostat, фазы размечать собственными
метками времени.

**Ход волны (CPU, 2026-09-30).** Реализовано и закоммичено в vektory79
(b99a103 "perf(scheduler): zero-copy flush pipeline for l2 tier";
session_tier.py + тесты, база волны 5f9abcc): zero-copy pwritev прямо из
регионов L1-пула (страницы сегмента несмежны из-за дедупа/refs -
смежность не нужна, разрозненные страницы покрываются набором iovecs;
pad из статического `_ZERO_BLK` - байт-идентичность блоба; чанки 512 iov;
цепочечный CRC32C по need-байтам - crc билдера перекрывается с записью),
конвейер групп (билдер-поток строит N+1, консьюмер пишет N;
`_PendingVolume` Condition + `_account_lock` leaf-lock; правило "билдер
не берёт `_lock`"), P3-семантика жертвы восстановлена bounded
drain-retry (граница 60 с с warning; fallback pending=0 может временно
перекрыть кэп на объём группы - только shutdown-flush,
задокументировано). Инвариант durable-до-журнала и окно потери
"группа" не тронуты; односегментный runtime `_write_blob` не тронут.
Тесты 72/72 + 70/70 (6 новых), fails-before точечным ревертом (3 теста
красные на базе), два ревью без блокеров, STOP GATE READY. Детали,
синхронизация и уроки - [P4-NOTES.md](P4-NOTES.md); методики
детерминированных тестов -
[deterministic-concurrency-tests.md](../../methods/deterministic-concurrency-tests.md).
Пре-реквизит выполнен (P6, dd349a6); железная рука выполнена
2026-09-30 - блок ниже.

# Задача P5: семантика shutdown-кэпа (стирание L2 при over-cap)

**Цель.** Graceful-стоп при used > кэпа больше НЕ стирает живое: решение -
какое поведение правильное (см. Спецификацию; требуется решение пользователя
ДО старта), но любое из них исключает молчаливый discard+truncate всего L2.

**База наблюдений.** ARM2 №1 приёмки P2: used 80.61 GiB против кэпа 50 ->
discard 38 записей + truncate блоба 86.55 GB -> 0 за ~1-2 с (прод-L2 стёрт;
[P2-NOTES.md](P2-NOTES.md)). Железная приёмка P3: водяной знак 87.8 против
live 2.8 -> все demote REFUSED -> вырожденный стоп; главный усилитель
устранён фиксом cap-accounting fast-бута (ab3a117, session_tier.py:329),
корень остался. Инконсистентность admission: demote прошёл при 80.23,
отказ при 80.61 (разница - dead-байты): чек выглядит dead/space-зависимым.
Операционный эффект двух стираний: прод-L2 оператора потерян дважды
(sessions re-prefill).

**Якоря (de26ba1).** `session_tier.py`: `_demote` / `_reserve_blob_span`
(cap-чек с pending), `_evict_oldest_l2`, `flush_live`; `shutdown_tier`
(`cache.py`); лог "L2 cap reached, cannot demote seg N/M".

**Спецификация.** Зафиксировать решение с пользователем из трёх: (а)
частичный demote - пока влезает в кэп, остальное живёт в L1 до следующего
стопа; (б) кэп - только runtime-гейт, стоп-флаш не ограничивать кэпом (диск
растёт, но ничего не стирается); (в) сохранить wipe, но только по явному
флагу оператора + громкий лог + отчёт о размере потерянного. Отдельно:
сделать admission-чек детерминированным (устранить dead/space-зависимость)
и задокументировать.

**Приёмка.** HW-стоп при over-cap (сгенерировать L2 >= 20% поверх кэпа):
живое сохранено байт-в-байт по выбранной семантике, resume HIT, явный лог;
CPU-тесты семантики (fails-before: текущий код стирает); один PR.

**Ход волны (CPU, 2026-09-30): закрыта P5-минимумом - overflow-наблюдаемость,
LRU как есть (решение пользователя).** Исследование перед кодом: LRU-admission
уже в проде - жертву выбирает min по (last_validation, seg_id)
(`_evict_oldest_l2`), штамп освежают restore/consume_ticket/матч снапшотов,
бут восстанавливает его из ts журнала; стоп-флаш резервирует span через
`_reserve_blob_span`, который при капе эвиктит ровно столько старого L2,
сколько нужно флашу (с учётом pending), а отказ "L2 cap reached" достижим
только если группа не влезает в кэп даже после полной эвикции L2 - при кэпе
60 ГиБ и группах 1-2 ГиБ недостижимо. Исторический wipe был вырождением бага
cap-accounting fast-бута (исправлен ab3a117): после него admission
dead-независим. Опция (б) "кэп - только runtime-гейт" не делалась.
Реализовано и закоммичено (94e4783: session_tier.py +
tests/scheduler/test_session_tier.py): flush-локальный талли
`_FlushOverflow` (records/bytes/admitted) в слоте `self._flush_overflow`
(try/finally вокруг `_flush_groups`), одна лог-строка на фазу флаша при
эвикциях ("session tier: flush overflow: evicted N records / X.X MiB of
oldest L2 to admit Y bytes"), тишина иначе; аккумуляция - один писатель на
поле, чтение после join билдера (не self._counters, урок P4). Тесты 82/82 +
70/70 (3 новых: одна строка при cap-эвикциях, тишина без эвикций,
drain-retry эвикция в тот же талли). Тайминги over-cap стопа (доминанта -
компакт, оценка 55-90 с при live 51 GiB; в проде dead ~60% блоба), отказ от
опции (б) и отложенная железная рука - [P5-NOTES.md](P5-NOTES.md).

   строительством CUDA-контекста - кольцо живёт в своём потоке/наборе

# Задача P13: durable-tombstone записи в журнале L2 (быстрый шатдаун на большом live)

**Цель.** Убрать обязательную компакт-переписку live из шатдауна на большом
live: сейчас шатдаун-компакт 33.7 с / 2.02 ГБ/с @ 31.95 GiB (P11-iron),
runtime-компакт при срабатывании даёт паузу ~live/3 ГБ/с ~ 11 с @ 32 GiB.
Сделать discard долговечным НЕМЕДЛЕННО (tombstone), чтобы компакт не был
единственным носителем durability удаления - и шатдаун-компакт стал
опциональным.

**База наблюдений (P11-iron, 2026-10-02).** Бюджет-дефер компакта структурно
ломает discard-durability: без компакта discard недолговечен -> полный
реплей следующего бута воскрешает вытесненное -> беговая дорожка
"вытеснение -> deferral -> воскрешение -> повторное вытеснение" (вариант (а)
P11 реализован и откатен - запоминающий урок). Честный шатдаун на HEAD
38-52 с; компакт-фаза 33.7 с при device 2.02 ГБ/с и util 86% - диск почти
насыщен, ускорять сам переписчик бессмысленно (P11). Руки лежали в
git-игнорируемом `.tasks/boot-shutdown-io/p11-iron/` (после клона считаются
утраченными); числа - здесь и в [P9-NOTES.md](P9-NOTES.md), раздел
"Коррекция P11-iron".

**Якоря (перепроверены по дереву на HEAD).**
`python/freetoken/scheduler/session_tier.py`: формат журнала - crc-обрамление
`struct.pack("<II", len, crc32) + payload` (JSON), версионирование `crc_alg`
(P3); `replay_journal` (:1632) - полный путь сеет P8-ledger, fast-path даёт
маркер P2; `_write_journal_new` (:1968) - переписчик журнала в two-phase
компакте P9 (`blob.bin.new` / `journal.log.new` / `swap.token`,
crash-таблица W1-W14); skip-условие маркера при `_dead_records > 0` (P9);
`stats_line` (:2254) - dead=Nrec/X MiB + holes=Y MiB.

**Спецификация.** Новый тип журнальной записи tombstone при discard/evict ->
discard долговечен немедленно -> шатдаун-компакт становится опциональным
(мёртвых записей для переписки нет). Дизайн-вопросы решить в волне:
(а) переживает ли tombstone compact - переносится в новый журнал или
семантика "применён - не переносить"; (б) взаимодействие с ключом выживания
(path_key, off, n) и P8 ledger - не задвоить учёт смерти записи; (в) реплей:
tombstone не воскрешает, только маркер; (г) skip-условие маркера P2 при
tombstones (маркер валиден, только если tombstone'ы долговечны); (д) рост
журнала от tombstones - потолок / компакт-порог по tombstone-объёму.
РИСК: раздувание журнала. НЕ ТРОГАТЬ: two-phase протокол P9 (W1-W14),
P8 гейт/ledger семантику, crc-версионирование, P6 env.

**Приёмка.** HW: шатдаун на большом live с большим discard-трафиком - время
шатдауна заметно ниже базы (компакт-фаза отсутствует или короткая);
воскрешений НЕТ (discard-durability через tombstone); байт-точность +
resume HIT; крэш-окно "tombstone недописан" -> конвергенция; CPU-батарея
зелёная. Один PR.

**Порядок.** Отдельная сессия; НЕ стартует без явного запроса пользователя.

**Ход волны (P13, 2026-10-04/05).** РЕАЛИЗОВАНА (HW-гейты взяты 2026-10-04;
коммит волны и 2 открытых решения - у пользователя). База vektory79 @ 9d91ec8,
волна некоммичена (session_tier.py, cache.py, тесты). Реализация: новый тип
журнальной записи {"t":1, path_key, off, n} (durable-tombstone; crc-обрамление
и формат старых записей не тронуты - старые журналы реплеятся бит-в-бит);
discard для seg.in_l2 пишет fsync'ed томбстоун немедленно тем же ключом
выживания (path_key, off, n), каким compact() строит keep-set; неудача
аппенда (OSError) -> `_marker_blockers` (старое поведение). Дизайн по пунктам
брифа: (а) компакт томбстоуны не переносит ("применён - не переносить");
(б) двойного учёта смерти нет - жертва кормит P8-ledger один раз (фильтром),
томбстоун сам в ledger не попадает; (в) реплей только убивает - сет-фильтр
порядко-независим и работает на ОБОИХ путях бута (fast-path включительно);
(г) B3-гейт маркера - блокируют только не-томбстоуннутые мёртвые
(`_marker_blockers`), а не любой `_dead_records > 0`; (д) рост журнала
ограничен существующим P8-гейтом (~100 Б/дискрад, новой ручки нет).
`shutdown_compact()` в cache.shutdown_tier: skip при dead>0 и blockers==0,
иначе классический компакт (уточнено 2026-10-05, решение пользователя: skip
только при blob_eof >= P8-floor, тиры ниже floor компактят безусловно). CPU:
tier-файл 122 passed (8 новых, 13 обновлены;
TP ревью x2 закрыты без правок прод-логики), fails-before 3 красных на старом
коде -> зелёные, батарея 2492 passed / 206 skipped / 5 известных Environment;
fsync-ассерт томбстоун-аппенда проверен в обе стороны.

HW A/B (кап 32 GiB, graceful стоп, старт - копия прод-тира 31.95 GiB live /
169 records, fill 40 диалогов x 9.3k, порт 18821): стоп 16.3 с vs BASE 55.7 с
(-39.4 с, -71%), компакт-фаза ОТСУТСТВУЕТ (.new runs 0; BASE: 37.8 с, blob
47.07 -> 31.95 GiB); флаш 4.0 с / 2.21 ГБ/с и teardown 11.3 vs 12.7 с -
паритет базы; BASE сходится с референсом P11-iron (51.7 с, 8%). Воскрешений
нет: пробы 35/35 эвицированных cached=0, 80 tombstoned stay dead, fast-path
"honored 80 tombstones"; байт-точность 159/159 общих сурвивор-спанов (md5
payload); resume HIT d36-d40 cached=9280. Цена per-discard fsync: филл 611 vs
603 с (+1.3%, в шуме); второй skip-стоп стабилен (18 с); P8-гейт подтверждён
на HW - рантайм-компакт следующего бута собрал дыры 47.07 -> 31.95 GiB при
идентичных md5 контента. Вердикт приёмки: гейты 1-3 ВЗЯТЫ (шатдаун,
воскрешения, байт-точность+resume), 4-5 PASS по CPU (torn-tombstone
конвергенция - матрица W1-W14; батарея). Метод-уроки: чистый тир 40 диалогами
не достигает капа 32 GiB (~15 GiB live) - большой live воспроизведён копией
прод-тира (cp -a, прод read-only); /media/ai переехал на nvme1n1 (вотчеры -
авто-детект девайса). Руки в git-игнорируемом
`.tasks/boot-shutdown-io/p13-tombstone/` (после клона считаются утраченными),
числа - здесь. Открытое (решения пользователя, НЕ закрывать): (1)

РЕШЕНО (пользователь, 2026-10-05): гейт уточнён, shutdown-компакт возвращён
