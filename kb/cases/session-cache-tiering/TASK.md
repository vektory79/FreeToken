# TASK: ярусный кеш сессий - вытеснение сегментов в RAM и SSD буферы фиксированного размера

Status: PLANNED (бриф составлен 2026-09-22 на вектории vektory79 @ d82274c; решения обсуждения
зафиксированы в [session-cache-tiering.md](../../topics/session-cache-tiering.md)).
Read CONTRIBUTING.md first - он обязателен; фичевые изменения сопровождаются тестами на новое
поведение, конфиги - без комментариев в коде.

## Context (измеренная база)

- Интерлив-промывка подтверждена железом 2026-09-22: при чередовании диалогов ход полностью
  теряет кеш (11/11 `#cached-token: 0` на дефолтном ratio 2.0); механизм - FIFO вытеснение
  GDN-снапшотов чужими коммитами + каскадное удаление KV
  ([interleave-cache-wash.md](../../topics/interleave-cache-wash.md)).
- Флаговый фикс `--linear-state-cache-ratio 8` измерен (Arm 2: 9/9 полных попаданий, ~20x), но
  пользователем НЕ принят: дорог по VRAM. Пулы L0 остаются тесными (дефолтный ratio).
- Эксплуатация: сессии часто 150-200k (64k - только мелкие субагенты), агентов может быть
  больше двух, параллельные сессии; при выключении сервера всё живое обязано понижаться в L2.
- Бюджеты пользователя: до 30 GiB RAM и до 100 GiB NVMe @ ~5 ГБ/с.
- Экономика: restore 150-200k сегмента ~30 мс (RAM) / ~280-344 мс (SSD) против 186-248 с
  re-prefill (~660-720x даже с SSD).

## Goal

При вытеснении из VRAM ценные границы сессий (tip + граница под последней дивергенцией +
запасная) не освобождаются, а понижаются в RAM/SSD буферы фиксированного размера; при
admission синхронно восстанавливаются; при выключении сервера всё живое сбрасывается в L2 и
переживает рестарт (первый ход после бута = HIT).

## Fixed design decisions (обсуждены 2026-09-22, менять через ревью брифа)

1. Перехват: pull-on-evict, селективный. Push-on-finish недостаточен: при 150-200k полезные
   grid-точки умирают mid-turn (~25 границ на ход при ~4-5 вытесняемых слотах).
2. Селекция: адаптивный набор {tip, граница под последней дивергенцией, запасная} - 3 снапшота
   ~443 MB + KV-путь сегмента.
3. Индексация: внешний контент-адресный стор; `HybridRadixCache`/`RadixTreeNode` семантически
   не меняются. Матч в сторе - инкрементальные хэши страниц промпта; restore = memcpy в
   свободные VRAM-страницы + штатный insert().
4. Restore-триггер: синхронно на admission (0.03-0.35 с); async - фаза 2.
5. Персистентность: append-only журнал на SSD (blob+fsync до записи журнала), boot = replay +
   ленивый restore; graceful shutdown = flush живого (~3.7 GiB ~ 0.74 с) + компакт чекпоинта;
   crash-safe по построению.
6. RAM: один кусок + mlock на старте. Конкурентность: refcount сегментов, сериализация restore
   на сегмент.

## Specification

### Единица и содержимое

Сегмент = KV-путь [0:N] + до 3 снапшотов на выбранных границах. Страницы хранятся
контент-адресно (ключ = хэш содержимого страницы; иммутабельность после коммита обоснована в
topics-статье) - дедуп общих префиксов субагентов и инкрементальные записи (~0.5 GB/ход с
дедупом против до 1.4 GB без).

### Компонент 1: SessionTierStore (новый модуль, предлагается `python/freetoken/scheduler/session_tier.py`)

- API: `probe(page_hashes) -> deepest (boundary_len, tier_handle) | None`;
  `offer(path_key, boundary_len, kv_pages, snapshot_slot | None)`; `restore(handle) -> pages +
  snapshot bytes`; `note_match(path_key, depth)`; `evict_store(n)` (LRU по последней
  валидации, согласован с VRAM `snapshot_lru`); `flush_live()`; `replay_journal()`.
- L1: pinned pool одним куском + mlock; L2: append-only blob-файлы + журнал в каталоге
  `--session-tier-dir`; O_DIRECT/io_uring для blob-чтения (dd-стиль капится ~1.5 ГБ/с).
- Политика переполнения: L1 full -> LRU-сегмент в L2; L2 full -> настоящий выброс старейшего
  (единственный путь к re-prefill).

### Компонент 2: перехват жертв (минимальная правка ядра - ТОЛЬКО аддитивная)

- `ensure_mamba_slots` / `evict_full` сегодня освобождают жертв
  (`python/freetoken/scheduler/cache.py:140-146` и `_free`). Добавить к `EvictResult`
  аддитивное поле - ключ пути каждой жертвы (расширение NamedTuple в
  `python/freetoken/kvcache/hybrid_radix_cache.py`; семантика матча/вытеснения не меняется,
  wash-пины d82274c остаются валидными).
- Решение keep/drop по адаптивному набору: tip пути; граница <= последней дивергенции пути
  (`note_match` обновляется на каждом admission из req.cached_len); новейшая не-tip граница.
  Группировка в "пути/сессии" - по корневой цепочке ключей страниц; для сессий с общим
  системным префиксом группировка грубее - документировать как осознанное приближение
  (уточняется при реализации, см. amendments-практику в
  [fix3-snapshot-lru-refresh/TASK.md](fix3-snapshot-lru-refresh/TASK.md)).
- Restore-интеграция: при shallow/cold матче admission пробует стор; восстановленные страницы
  и снапшот возвращаются в игру штатным insert()/cache_req-путём; бюджет admission прежний
  (restore потребляет те же страницы/слот, что и замещаемый re-prefill).

### Компонент 3: выключение/старт

- Graceful shutdown: flush живого в L2 + чекпоинт (лог-компакт). SIGKILL: replay журнала на
  буте, ленивый restore - бут не тяжелее сегодняшнего (~52 с FTW).

### Конфигурация

- `--session-tier-ram-gib` (default 0 = off), `--session-tier-dir` (path; off, если не задан),
  `--session-tier-ssd-gib` (cap). Off = поведение сегодняшнего дня бит-в-бит; все существующие
  пины и тесты не меняются.

### Фаза 2 (вне приёмки фазы 1)

Async-предвыборка; hardening конкурентности при mr>1 (refcount/reflock стресс-тесты);
компакт журнала по расписанию; метрики (hit-rate стора, байты ярусов); не-гибридные модели.

## Acceptance (фаза 1)

CPU:

1. Тесты стора: контент-адресация и дедуп; инкрементальные записи; LRU переполнения L1->L2 и
   выброс L2; журнал: replay после SIGKILL-симуляции (обрыв журнала), идемпотентность.
2. Тесты селекции: адаптивный набор (tip + под-дивергенция + запасная) на
   синтетической истории с переписываниями; ложное хранение старых grid-точек отсутствует.
3. Тесты перехвата: жертва в адаптивном наборе понижается (не освобождается); вне набора -
   освобождается как сегодня; restore восстанавливает байт-в-бит те же KV и снапшот (сверка с
   исходными байтами).
4. Off-режим: с выключенным флагом весь существующий гейт без диффов поведения
   (`uv run pytest tests/kvcache/radix tests/scheduler -m "not slow"`).

Железо (RTX 5090, пакет `.tasks/interleave-cache-repro/`, серийно):

5. Arm 3 (персистентность): прогон Arm-сценария -> shutdown -> boot -> первый ход каждой
   сессии = HIT (`#cached-token` > 0, wall ~restore-латентность, не re-prefill).
6. Arm 4 (масштаб): чередование двух сессий 150-200k на дефолтном ratio с tiering -> все
   не-холодные ходы = HIT или частичный матч с re-prefill хвоста <= ~8064 токенов; время хода
   << 186-248 с.
7. Байт-точность: ответ модели на восстановленной сессии идентичен ответу на живой
   (детерминированный greedy-запрос).

## AMENDMENT (user decision, post железа, 2026-09-22): приёмка 7 - поведенческая точность

Пункт 7 ("ответ модели на восстановленной сессии идентичен ответу на живой") заменён на
критерий поведенческой точности:

- (a) восстановленный ход = HIT (cached > 0) за время restore-латентности, не re-prefill;
- (b) точность KV+снапшот доказана байт-в-байт на CPU: roundtrip стора при restore,
  включая буферы квантовочных масштабов;
- (c) нарушений целостности кеша нет во время железных прогонов (page accounting чист).

Обоснование (измерено, журнал вне репозитория:
[.tasks/session-cache-tiering/arm3_console.log](../../../.tasks/session-cache-tiering/arm3_console.log)):
greedy-декод на этом движке не бит-детерминирован ни между чанкингами prefill, ни между
бутами. Arm-3: расхождение cold-prefill против restore-пути внутри одного бута - с символа
36; restore-путь бут A против бута C (идентичный путь) - с символа 94 (~22 одинаковых
токена). Реальная порча состояния перевернула бы ответ с токена 1: это дрейф
детерминизма декодера, а не деградация кеша.

Отметка исполнения (2026-09-22): Arm 3 и Arm 4 выполнены.

- Приёмка 6 (масштаб, Arm 4) PASS: две сессии 150k, 8/8 не-холодных ходов = HIT,

- Приёмка 7 PASS по изменённому критерию (см. выше).
