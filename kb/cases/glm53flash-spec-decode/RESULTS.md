# W0: зонд цены verify-батча (step_cost(M)) - вердикт NO-GO

**Вердикт: NO-GO (2026-10-10).** Кейс [TASK.md](TASK.md) закрывается по его
правилу: "NO-GO закрывает кейс таблицей чисел - валидный исход". Ни одна
глубина draft не проходит вердикт-формулу: замер R выше порога уже для M=2
даже при идеальном acceptance; для M=4 превышение в 1.6x; verify M>=4 на
целевом профиле 64k в 32 GiB к тому же нереализуем (slot-floor + OOM + wedge).
W1-W5 не начинаются.

## Вопрос и метод зонда

Вопрос W0 (из брифа): во сколько раз дорожает шаг гибридного MoE при M
токенах на шаг (уникальные пары (слой,эксперт) растут сублинейно от M x 8,
hits в VRAM-слотах бесплатны, GEMM на CPU эффективнее GEMV на байт)?

- Зонд: N параллельных decode-потоков через ft serve (continuous batching
  разделяет MoE-кэш) = ВЕРХНЯЯ оценка цены verify-батча из M токенов:
  маршруты независимых потоков пересекаются меньше, чем M продолжений одной
  цепочки, поэтому реальный verify MTP будет ДЕШЕВЛЕ замера -
  консервативный гейт.
- Рука: N in {1,2,4,6} x {hybrid, offload} x {32k, 64k}. Каждый поток - ОДИН
  streaming-запрос: prompt = distinct rotated filler длины CTX (уникальные
  контенты на руку против session-tier L2 restore), temp 0 / top_k 1,
  max_tokens 768. Single-request паттерн вместо fill+resend: при N x 64k
  radix-дерево + активный KV вдвое превышают пул 400k -> L-drop исказил бы
  декод; декод-фаза при этом идентична якорной.
- Метрика: p50 ms/шаг декод-фазы в ЧИСТОМ окне. Старт = max(вторых кадров
  потоков, timestamp последнего "Prefill batch" движка + 1s) - первый
  SSE-кадр приходит ДО конца префилла (кадр admission); конец = финиш самого
  быстрого потока (гарантия полного батча M). p50 по pooled гэпам окна:
  движок отдаёт кадры всех потоков на границах шага, гэпы синхронны;
  496-3057 шагов на руку. tok/s вторична - агрегат по окну. p50 первична,
  last-chunk артефакт не трогается.
- Якорный конфиг ft serve (из брифа): memory-ratio 0.82, mpl 8191,
  moe-cache-auto, kv-reserve 400k fp8, moe-cpu-threads 16, tier 10/50.
- 62k-калибровка: hybrid 52.0 / offload 71.4 ms/шаг - в пределах шума от 64k
  ячеек; контекстный градиент 62k -> 65.6k < 1.5%: цена шага от контекста
  почти не зависит, 62k-ячейка не нужна.
- 2k-пара для N>=4: единственный режим, в котором N>=4 вообще работает на
  этом риге (см. "Блокеры") - prompt ~2.2k ток <= mpl 4096, каждый поток
  префиллится ОДНИМ чанком; ratio 0.90 (n1/n4) / 0.92 (n6), 512 max_tokens.
- Протокол: сериальные руки, один ft serve за раз (VRAM-протокол); boot
  каждой руки верифицирован (hybrid fetch fraction 30.7%, не cap-1; pool
  split; pinned cores); teardown SIGTERM -> grace 45s -> SIGKILL, census
  чист, GPU возвращается к ~0.9-1.2 GiB. Харнес: probe_w0.py (адаптация
  .tasks/decode-research/run_arm.py) + campaign_w0.py + pair2k.py.
- Покрытие: все 8 рук N in {1,2} (обе стратегии, оба контекста) на якорном
  конфиге - полная парная база для R_2; R_4/R_6 - измеренная пара на 2k.
  N>=4 на 32k/64k на этом риге НЕВЫПОЛНИМЫ - четыре блокера ниже.

## Отклонения N=1 от якорей брифа

- hybrid 64k: 18.75 tok/s (52.7 ms) против якоря 18.04-18.65 tok/s -
  +1.7%, попадание в якорный диапазон, ок (32k: 18.25 tok/s).
- offload 64k: 14.18 tok/s (70.7 ms) против якоря 12.97-13.72 tok/s - на
  +3-8% быстрее якоря; правдоподобная причина: offload-якорь эры до T2/C-L1
  (2026-09-26), часть выигрыша T2 достаётся и offload-ноге - дрейф, а не
  аномалия.
- База R_2 валидна: обе стратегии стартуют из якорной/объяснимой точки.

## Блокеры N>=4 на 32k/64k (воспроизведены; код движка не трогался)

1. **Slot-floor gate moe-cache-auto.** План слотов MoE-кэша падает с N
   (1167 @N1 -> 950 @N4 -> 934 @N6) ниже минимума 1059 layer-0-width
   слотов; порог проходят только ratio >= 0.89 (N4) / 0.915 (N6).
   Исторический якорь 0.82 жив ТОЛЬКО для N<=2 (при N=1 план 1167 >= 1059).
2. **OOM банков.** При ratio 0.92 на 64k загрузка банков падает по CUDA OOM;
   спасает mpl 4096 (меньше пик активаций префилла) -> N=6 бутится
   (кэш 1082 >= 1059, GPU после boot 29.7/32 GiB).
3. **WEDGE - главный блокер, баг движка (материал для отдельного issue).**
   Repro-условия: `--max-running-requests >= 4` И МНОГОчанковый префилл
   (prompt > mpl). Симптом: движок делает РОВНО один чанк префилла и
   замолкает навсегда - ни Decode batch, ни следующего Prefill batch, потоки
   висят до таймаута. Воспроизведён 4 раза (hybrid/offload, 32k, конфиг
   0.92+mpl4096): с moe-prefill-overlap и без него, при одновременном и
   разнесённом на 12 s входе запросов, на холодных L2-контентах. Контроли:
   N=1/2 на том же конфиге работают; N=6 с одночанковыми промптами
   (2.2k <= mpl) работает. Клин = (max-running-requests >= 4) AND
   (multi-chunk prefill) - баг шедулера, вне претенции W0 (зонд шёл без
   кода движка).
4. **Явный --moe-cache-size мёртв для этого файла.** Обход гейта явным
   размером не работает: explicit-единицы требуют >= 8510 слотов (~90 GiB)
   для fund всех signature-group floors - путь нереализуем на 32 GiB.

## Вердикт-формула, применённая явно

Формула брифа: приёмка draft-глубины K (M=K+1) требует
step_cost(M)/step_cost(1) < ожидаемый acceptance A (токенов на шаг);
e2e-гейт кейса +12-15% эквивалентен R <= A/1.12.

- **M=2 (K=1):** R_2 = 1.90-1.96 (якорный конфиг, прямое измерение). Потолок
  acceptance при K=1 = 2.0 ток/шаг -> порог R <= 1.79. Замер ВЫШЕ порога
  даже при идеальном acceptance; при реалистичном greedy (0.6-0.75 ->
  A = 1.6-1.75) speedup = 0.83-0.91x, т.е. ЗАМЕДЛЕНИЕ. Структурный fail
  гейта +12-15% ещё до MTP-специфики.
- **M=4 (K=3):** R_4 = 3.76 hybrid / 4.89 offload (2k-пара; для 64k только
  хуже - fetch растёт вместе с уникальными парами). Порог 1.61 (A=1.8) -
  2.32 (A=2.6). Превышение в 1.6x даже при оптимистичном A=2.6 и нулевом
  запасе.
- **M=6 (K=5):** R_6 = 6.10 / 6.72 - хуже.
- **Offload:** R строго выше гибрида на всех M -> offload+MTP не обгоняет
  даже сегодняшний гибрид (согласуется с chat-анализом брифа: брейк-ивен
  A >= 1.44 x g(M)).

## Оговорка честности (обязательна)

N-потоковый зонд - ВЕРХНЯЯ оценка цены verify: маршруты независимых потоков
некоррелированы, реальный verify MTP на продолжениях одной цепочки дешевле.
NO-GO означает: для опровержения нужен дисконт коррелированных маршрутов
>= 1.62x для M=4 (>= 1.22x для M=2 против идеального A) - величина нигде не
измерена; экосистемные приоры против (Gemma4 MoE no-gain даже на полном GPU -
llama.cpp #23398; ik_llama.cpp #1513 - 2x LOSS при acceptance 0.573), а её
получение требует реализовать W1+W2 - это уже не зонд.

## W1-narrow: A/B verdict (2026-10-10) - NO-GO on target profile; инфраструктура остаётся

**Постройка.** n-gram drafter (order 2, lookup без lookahead - семантика Stage 0)
+ greedy verify-каркас в scheduler: батч K+1 позиций одного запроса через
prefill-конвейер, acceptance argmax, GDN-откат снапшотом слота
(LinearStatePool.copy_from в scratch), метрики accepted/drafted в decode-логе,
флаги --spec-decode/--spec-k/--spec-ngram-order (default OFF). Review: 2 MAJOR
исправлены (кормление драфтера на plain decode-drain; счётчики non-hybrid
partial-reject), test integrity подтверждена (fails-before реальные, вакуумных
нет). В ходе A/B найден и снят ТРЕТИЙ молчаливый гейт: _maybe_spec_verify_batch
возвращал None при page_size!=1; для латентного KV-внимания (пин page_sizes=(64),
attention/__init__.py:158 + форс engine.py:398-401) принят leak-until-finish:
supports_spec_verify без page_size==1, reject при page_size>1 не освобождает
страницы (<= ceil((K+1)/64) стр/reject, wholesale free на finish). Полный набор
падений тестов идентичен до/после волны (все - предсуществующие/environment).

**A/B** (парное окно: 64k fill radix-reuse, temp 0, 768 tok, hybrid якорный
конфиг):

- off2 (букенд): 18.409 tok/s (p50 53.4 ms)
- k1: 18.379 (-0.16% vs off2)
- k2: 18.712 (+1.65% vs off2) - разброс в пределах шума пары +-1.7%
- acceptance = 0: драфтер ни разу не предложил кандидата, 0 verify-шагов в обеих
  ON-руках -> ON == OFF по построению. kpool-ring кавэт невалидируем (reject'ов нет).

**Корень (урок, главный результат волны).** Stage-0 офлайн-метод мерил
САМОПЕРЕСЕЧЕНИЕ потока filler (93% совпадений), а не СОГЛАСИЕ МОДЕЛИ с таблицей:
живой жадный декод продолжения не воспроизводит n-граммы шаблона (биграммы декода
вне таблицы, probe tail вне словаря таблицы). Самопересечение текста -
НЕ валидный прокси n-gram acceptance; перед постройкой drafting-инфраструктуры
мерить model-vs-table agreement на живом декоде.

**Интерпретация.** Высокое radix-reuse ПРЕФИКСА (якорный профиль 64k) не означает
ПОВТОРЯЕМОСТЬ ВЫВОДА: на целевом профиле кейса n-gram drafting не может дать
выигрыш (acceptance 0), но и не теряет (overhead ниже шума пары). Гейт волны
+12-15% - NO-GO на этом профиле. Каркас default-OFF и может окупиться только на
нагрузках с действительно повторяемым ВЫВОДОМ (шаблонная/структурированная
генерация). Для боевого temp 1.0 дополнительно нужен W3 (rejection sampling).
