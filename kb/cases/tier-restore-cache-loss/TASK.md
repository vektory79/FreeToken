# Полная потеря кеша при работе агента: restore-счётчик растёт, кеш не восстанавливается

**Вердикт исследования.** Симптом "кеш не восстановился, но счётчик восстановлений
инкрементировался" объясняется тремя сцепленными механизмами на сервере плюс
клиентским триггером, который их активирует:

1. Счётчик `restore=N(l1)/M(l2)` в tier-метриках считает ПОПЫТКИ, а не успехи
   (`scheduler/session_tier.py`, комментарий у инкремента: "counts ATTEMPTS:
   try_restore may still discard the result at its boundary/snapshot gate").
2. После инкремента гейт в `CacheManager._restore_tail` (`scheduler/cache.py`)
   молча отказывает восстановление, если у сегмента нет GDN-снапшота РОВНО на
   глубине матча (`_tier_snap_bound.get(handle.path_key) != depth or not snaps`).
3. Глубина матча, которую вернул probe, в эпизодах заведомо не совпадает ни с
   одной границей сегмента: probe (`session_tier.py probe()`) матчит ЛЮБУЮ
   страницу сегмента (индексируются все страницы, `_touch_index`) и останавливается
   на самой глубокой общей странице запроса и стора - mid-span матч, который
   гибрид обслужить не может в принципе (снапшот обязан сидеть на глубине резюма).

Клиентский триггер: история промпта переписывается между ходами в моменты
мутаций контекста клиента - `save_memory`/`update_memory`, сообщение
пользователя, `move` файлов. После переписывания матч дерева = 0 (все живые
снапшоты дерева сидят глубже точки дивергенции - окно FIFO последних границ),
полный re-prefill неизбежен на текущем коде.

Открытый вопрос ровно один: ГДЕ в промпте происходит переписывание (первые
страницы: recalled-memories/env блоки клиента - тогда полный re-prefill
оправдан и неустраним сервером; или mid-history ~84-90% глубины, как в кампании
fix3 - тогда ярус МОГ бы обслужить резюме от хранимой границы, но не делает
это из-за пунктов 1-3). Закрыт серией P0 2026-10-07: ответ зависит от
семейства триггера, см. раздел "Результат P0" в спецификации ниже.

### Цепочка механизма в коде (все шаги сверены на f5bf1cb)

1. `kvcache/hybrid_radix_cache.py match_prefix`: матч урезается до глубочайшего
   узла пути с ЖИВЫМ снапшотом. Дивергенция ниже самой глубокой живой границы
   (окно FIFO ~5 живых слотов, все на границах 90k+) даёт `cached_len=0`, даже
   если KV-страницы дерева целы.
2. `scheduler/cache.py _tier_admission`: дивергенция сессии записывается как
   `st[1] = cached_len` - то есть 0 (см. шаг 1). Следствие: условие
   под-дивергентного слота адаптивного набора `vp.boundary_len <= st[1]` в
   `_tier_offer` никогда не выполняется -> слот `st[3]` не заполняется -> в
   сторе НЕТ границы, способной обслужить mid-span резюме.
3. `scheduler/cache.py try_restore`: `probe` находит самую глубокую общую
   страницу запроса и стора. Все страницы сегмента в индексе
   (`session_tier.py _touch_index`), поэтому mid-span страница маскирует
   boundary-exact сегмент на меньшей глубине (break на первом d с любым
   матчем; предпочтение `boundary_len == d` - только tie-break внутри одного d).
4. `session_tier.py restore()`: байты читаются, `restore_l1/restore_l2`
   инкрементируются ДО гейтов хвоста (комментарий в коде честно называет это
   "counts ATTEMPTS").
5. `cache.py _restore_tail`: гибридный гейт требует снапшот ровно на depth ->
   тихий `return None`, страницы/слот возвращаются пулам, запрос падает в
   полный re-prefill. Наблюдаемое: счётчик вырос, кеш нет.

Шаги 2-3 вместе означают: даже при mid-history дивергенции (когда ярус МОГ бы
отдать резюме от хранимой границы с re-prefill только хвоста) восстановление
невозможно по построению - и в сторе нечего отдавать (шаг 2), и probe не
возвращает граничный сегмент (шаг 3).

## Родственные семьи симптома (в этом логе не покрыты)

- Переключение субагент/основной агент: отдельные чаты с тем же статическим
  преамбулом имеют ОБЩИЙ ключ сессии (`_tier_sessions` keyed by chain[0] -
  задокументированное приближение фазы 1) - состояние сессии алиасится между
  чатами, tip одного чата вытесняет tip другого. Плюс FIFO-промывка живых
  снапшотов дерева коммитами субагента
  ([interleave-cache-wash.md](../../topics/interleave-cache-wash.md)).
  Для подтверждения нужен лог окна с реальным переключением (запросы субагента
  в логе отсутствуют в предоставленном окне 22:24-23:28).
- Наличие живого снапшота дерева на пути - обязательное условие ненулевого
  матча; ярус это компенсирует только при сегменте, чья граница РОВНО на
  глубине резюма (E1: probe в вчерашний сегмент, гейт отказал - глубина
  общего преамбульного матча не совпала с вчерашней границей).

## Спецификация исправления (фазы)

### P0 - честная телеметрия и закрытие открытого вопроса (первая волна)

- Счётчики: `restore_ok` / `restore_refused` рядом с существующими
  `restore_l1/l2` (инкремент попыток оставить, статистику разделить).
- На отказ гейта `_restore_tail` - одна лог-строка: probe depth (страницы),
  tree `cached_len`, `owned_prefix` глубина (истинная точка дивергенции:
  дерево владеет KV-страницами вплоть до неё даже при 0 живых снапшотов),
  `snap_bound[path_key]`, короткий хэш chain[0].
- Аналогично на отказе `try_restore` ДО вызова restore (нет свободных страниц/
  слота) - чтобы отличать нехватку ресурсов от гейта снапшота.
- Приёмка P0: одна серия воспроизведения эпизода (сервер + реальный паттерн
  клиента: ход с `save_memory`, уточняющий вопрос, `move`) даёт ответ, где
  дивергенция. Если `owned_prefix` ~ первые страницы - полный re-prefill
  оправдан, сервер не виноват, пункты P1-P2 превращаются в наблюдаемость;
  если mid-history - P1-P2 обязательны.

- Оговорка: место переписывания при РЕАЛЬНЫХ save_memory/update_memory в
  клиенте не наблюдалось - серия даёт механизм по локациям, а не фактический

Вердикт: для семейства move/вопрос пользователя (E3/E4) дивергенция

полный re-prefill оправдан, там P1/P2 дали бы только наблюдаемость.

### P1 - probe не должен возвращать необслуживаемый матч

- Для гибридного менеджера: mid-span совпадение (d внутри сегмента, снапшот
  не на d) не возвращать как результат probe; продолжить обход к меньшим d в
  поиске boundary-exact сегмента. KV-only менеджерам mid-span restore корректен
  (транкейт страниц) - поведение для них не менять.
- Либо (минимальный вариант): на отказе гейта повторный probe с исключением
  mid-span матчей.

### P2 - истинная дивергенция в адаптивном наборе

- `_tier_admission` записывает дивергенцию сессии по `owned_prefix` глубине,
  а не по урезанному матчу - тогда под-дивергентный слот `st[3]` заполняется
  и в сторе появляется граница, ближайшая к точке дивергенции.
- Следствие: ход после переписывания истории восстанавливается от хранимой
  границы B <= дивергенции, re-prefill только хвоста [B:end] вместо всего
  промпта.

### P3 - семейство субагентов (отдельная волна, после P0)

- Лог-окно с реальным переключением субагентов; проверить алиасинг
  session-ключа (chain[0] общий для всех чатов) и FIFO-промывку дерева.
- Решение о группировке сессий (chain[0] + длина общего префикса, либо
  явный session id) - отдельно, после данных.
