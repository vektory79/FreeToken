# T2 lever #2: анатомия межвызовных гэпов декод-шага (gap anatomy)

Status: RESEARCH 2026-09-27; коммитов нет, код не менялся. Ветка кампании
[TASK.md](TASK.md) -> Step 0 [step0-phase-table.md](step0-phase-table.md) ->
Wave 1 [wave1-ab-summary.md](wave1-ab-summary.md) (lever #1 t2d принят,
пулы [15,1,4]). Этот документ закрывает lever #2: что живёт в межвызовных
гэпах, почему и что с этим можно сделать.

## TL;DR (вердикт)

- **Premise брифа опровергнут кодом**: PCIe-фетч НЕ живёт в гэпах - он уже
  сегодня выпускается ПОСЛЕ doorbell'а пула и прячется под окно CPU-ноги
  ([moe.py:330](../../../python/freetoken/layers/moe.py) submit ->
  [moe.py:338](../../../python/freetoken/layers/moe.py) copy_missing).
  Цена полной сериализации уже измерена arm'ой ov0: -23.5%.
- **Гэпы (~13.9 ms/шаг) - это не простой, а серийная GPU-цепочка**:
  attention следующего слоя (KDA light ~0.28 ms / DSA heavy ~0.43 ms,
  бимодально ровно по раскладке 34 KDA + 11 DSA), dense/router, add-ядро
  и 3 мелких D2H-копии submit'а на слой. Истинный GPU-idle в гэпах мал
  (~2.4: doze + накладные - раздел 3).
- **Единственная новая измеренная утечка - doze-задержка координатора
  минорного пула**: ~1.0 ms/шаг (грань p0->p1 = 1.31 ms против 0.27-0.43
  у соседей). Механизм: hot-window 50 ms
  ([cpu_moe_ext.cpp:2934](../../../python/freetoken/kernel/csrc/cpu_moe/cpu_moe_ext.cpp))
  короче шага 57 ms между вызовами pool1 -> координатор спит каждый шаг.
- **nsys уточнил масштабы** (раздел 3): PCIe-фетч - 28.7 ms/шаг GPU-времени
  копий (не 6-8, как считалось), полностью спрятан под окнами пула; GPU занят
  77% шага; истинный простой 12.8 ms/шаг = wait-slack ожидания флага пула
  внутри окон (~10-12, несжимаем без ускорения CPU-ноги) + doze ~1 +
  launch/мемоп/межшаговые накладки ~1.5.
- Блокирующая зависимость цепочки - **истинная data-dependency**
  (flag(L) -> add -> attention(L+1) -> router -> indices -> pool(L+1)),
  а не произвольный порядок запекания графа. Перекрыть её нечем: единственная
  пара независимых ресурсов (PCIe-фетч vs CPU-пул) уже совмещена.
- **Рекомендация**: A/B механизма C1 (doze-fix координаторов минорных пулов):
  ~0.9-1.0 ms/шаг (+1.6-1.8% декода), самый дешёвый и безопасный. Честно:
  это ниже гейта +5% из TASK.md; решение о принятии такого микро-выигрыша -
  за пользователем. Кандидаты (i)/(ii)/(iii) из брифа закрываются разделом 5.

## 2. Что именно лежит в гэпах

### 2.1 Серийная GPU-цепочка (~12.9 ms/шаг)

Между флагом слоя L и doorbell'ом слоя L+1 стрим обязан исполнить
(каждый узел ест выход предыдущего - см. раздел 4):

- add партиалов: gpu_routed + cpu_routed ([moe.py:352](../../../python/freetoken/layers/moe.py));
- attention слоя L+1: GDN/KDA на light-гранях, DSA-indexer + gathered-KV на
  heavy-гранях (@64k контекста - дорогая часть);
- dense GEMV/MMVQ q8_0 + router + fused_topk;
- 3 мелких D2H-копии submit'а (x, ids, w -> pinned,
  [cpu_executor.py:963-966](../../../python/freetoken/moe/cpu_executor.py));
- фронтенд-мемопы doorbell (done[slot]=0; ready[slot]=1,
  [cpu_executor.py:970-977](../../../python/freetoken/moe/cpu_executor.py)).

Оценка состава граней без поядерных данных: light 0.27 ms = KDA + dense +
router + add + D2H + мемопы; heavy 0.43 = то же + DSA-блок. Поядерное
приложение nsys - раздел 3: chain-классы суммарно 11.52 ms/шаг
(dense_gemv 6.67, gdn/mhc 1.91, add/copy 1.36, topk/router 0.76, quant 0.32,
dsa 0.30, ensure_experts 0.16).

### 2.2 PCIe-фетч: 0 ms в гэпах (уже спрятан под пул)

Порядок в `_decode_hybrid`
([moe.py:305-352](../../../python/freetoken/layers/moe.py)):
`decode_submit` (:330, дверной мемоп - пул стартовал) -> `copy_missing`
(:338, fused H2D-gather ядро, читает host-банки через PCIe) -> GEMM (:341)
-> `decode_sync` (:350, WAIT(done[slot])) -> add (:352). То есть копии
физически исполняются ВНУТРИ окна busy пула L+1 и складываются с его
compute-окном. Доказательство не только кодом, но и A/B: FREETOKEN_HYBRID_OVERLAP=0
(синхронизация ДО копий) стоил -23.5% (16.29 -> 12.46 tok/s) -
это и есть цена положить скрытую работу (копии + MoE-GEMM) на ладонь.
nsys-измерение: копии занимают 28.7 ms/шаг GPU-времени (раздел 3) - старая
оценка 6-8 ms занижала их в 4 раза, прятать их было НЕЧЕМ кроме окна пула.
В гэпах фетча нет. Кандидат (i) брифа "выпустить фетч сайд-стримом" -
уже продакшн-поведение.

### 2.3 Doze-задержка координатора pool1: ~1.0 ms/шаг

Грань p0->p1 = 1.308 ms против 0.27-0.43 у всех соседних граней. Механизм:
координатор каждого экзекьютора крутит
[coordinator_loop](../../../python/freetoken/kernel/csrc/cpu_moe/cpu_moe_ext.cpp)
(:2921): горячий spin только 50 ms после своего последнего флага
(kHotWindow, :2934), дальше - timed-sleep doze до 2 ms (kSleepCapUs=2000,
"discovery delay on the FIRST MoE layer after an idle period"). pool0
флагается каждые ~1.4 ms - не спит никогда. pool1 вызывается 1 раз/шаг:
интервал между его флагами ~57 ms > 50 ms -> координатор doze'ит каждый
шаг, discovery-задержка ложится в грань перед pool1 (CPU увидел дверной
флаг поздно; стрим тем временем уже прокрутил копии+GEMM этого слоя, поэтому
наружу торчит только избыток ~0.9-1.0 ms). p0->p2 (0.322) - вторая
легкая утечка того же класса: pool2-slot1 вызывается в конце шага, его
координатор горячий (35 ms с прошлого флага < 50), поэтому торчит только
0.03-0.05.

Итого классификация бюджета гэпов t2d:

| статья | ms/шаг | метод |
|---|---|---|
| серийная GPU-цепочка (KDA-грани) | ~8.0 | трейс, 28 x 0.28 |
| серийная GPU-цепочка (DSA-грани) | ~3.8 | трейс, 9 x 0.43 |
| doze координатора pool1 | ~0.9-1.0 | грань 1.31 против соседей 0.27-0.43 |
| прочие дверные/мемоп-латентности | <=0.2 | остаток граней p1->p2/p2->p0 |
| **истинный GPU-idle в гэпах** | **~2.4** | doze ~1.0 + launch/мемоп-гэпы цепочки + межшаговый хост (раздел 3) |
| **итого гэпы** | **13.93** | конверт - busy |

Проверка перекрытия фетча арифметикой: объём фетча ~0.68 GiB/шаг при f=30.7%;
в гэпах 0 ms -> весь прячется в busy 43.5 ms; эффективные 41.5 GB/s
совмещённой доставки из TASK.md согласуются.

## 3. nsys-верификация (поядерные числа)

Метод: одна аппаратная проба `nsys profile --delay 60 --trace=cuda
--cuda-graph-trace=node` над точным якорным конфигом (probe_nsys_gap.py,
переиспользует run_arm). Мини-проба ДО пробы подтвердила сбор (rc=0, репорт
223 KB, 7 ядер включая replay CUDA-графа) - протокол против тихого
no-collection. Первая попытка провалилась и задокументирована: --duration=75
завершил приложение через ~72 s от старта (boot 68 s, delay 80 ещё не истёк) -
коллекция не началась, репорт 234 KB пуст; воркеры двигателя пережили nsys
(re-parent) и держали 25.7 GiB VRAM - добиты по compute-apps pid, census
чист. Вторая попытка: ready 99.3 s, fill 65585 токенов за 4.35 s, декод 468
токенов 17.76 tok/s (p50 55.3 ms; этот boot классом быстрее рук wave 1 -
дневная вариация, структура та же); teardown SIGTERM + свип воркеров по
compute-apps; census-clean, VRAM 1265 MiB.

Анализ: sqlite export (240 MB, 1.84M ядер), пер-инстанс классификация
(analyze_nsys_gap2.py). Декод-бёрст = последний непрерывный бёрст инстансов
_ensure_experts_hybrid_kernel (ровно 1/слой/шаг): 19,656 / 42 = 468 шагов,
span 26.30 s.

Пер-шаговый бюджет (mean по 468 шагам):

| статья | мс/шаг | комментарий |
|---|---|---|
| wall региона | 56.20 | span бёрста / 468 |
| kernel busy | 43.29 | занятость GPU 77% |
| - chain-классы | **11.52** | dense_gemv 6.67 (402 пуска - проекции attention, q8_0 MMVQ), gdn/mhc 1.91, add/copy 1.36, topk/router 0.76, quant 0.32, dsa 0.30, ensure 0.16 |
| - pool-window классы | **31.01** | pcie_copy (fast_index_copy, 1/слой) 28.66, moe_gemv (moe_vec) 2.35 |
| cudaMemcpy | 0.13 | фетч идёт копия-ЯДРОМ (zero-copy чтение host-банков), не memcpy; D2H 127/шаг, H2D 52/шаг - все мелкие |
| **idle** | **12.78** | раскладка ниже |

Три ключевых измерения:

1. **PCIe-фетч = 28.7 ms/шаг GPU-времени, не 6-8.** Один fused
   fast_index_copy на слой, 0.68 ms среднее; 0.68 GiB / 28.7 ms = ~24 GB/s =
   bench pcie_ov 22.1 (TASK.md). Всё спрятано под окнами пула: ~0.74 ms
   GPU-работы (копия 0.68 + moe_vec 0.06) на слой внутри окна ~1.03 ms (pool0).
2. **Цепочка = 11.5 ms/шаг** - сходится с CPU-часами гэпов 13.9 (wave-1
   трейс): 11.5 ядер + doze ~1.0 + ~1.4 накладных. Грань p0->p1 1.31
   объясняется полностью. Самый тяжёлый класс цепочки - dense_gemv (q8_0
   MMVQ-проекции), а не attention: DSA-ядра всего 0.30 ms/шаг.
3. **Истинный простой 12.8 ms/шаг**: основная часть (~10-12) - WAIT(done)
   внутри окон пула (GPU закончил копии+GEMM и ждёт флаг; пул у потолка
   48.7 GB/s - несжимаемо без ускорения CPU-ноги); остальное - doze ~1,
   межшаговый хост (сэмплинг), launch-гэпы и мемоп-латентности ~1.5. Для
   pool1 часть копий (0.68) сдвигается за пределы его короткого окна (0.17)
   и исполняется прямо во время doze - потому наружу торчит только избыток.

Смена статуса старых оценок Step 0/T1: "фетч 6-8 в гэпах, ядра 8-9, остаток
idle" -> "фетч 28.7 спрятан в окнах пула, цепочка 11.5 в гэпах, idle 12.8 =
wait-slack + doze + накладные". Противоречия с фазовым трейсом нет: это два
разных окна отсчёта (CPU-часы между вызовами vs GPU-часы внутри окон).

## 4. Блокирующая зависимость: data-dependency, а не запечённый порядок

Точная цепочка на слой L (файл:строка):

1. [cpu_executor.py:991-993](../../../python/freetoken/moe/cpu_executor.py)
   WAIT(done[slot]>=1) - фронтенд-мемоп, стрим стоит до флага пула;
2. [moe.py:352](../../../python/freetoken/layers/moe.py) add(gpu_routed,
   cpu_routed) - читает H2D-результат пула ([cpu_executor.py:997](../../../python/freetoken/moe/cpu_executor.py));
3. attention+dense+router слоя L+1 - читают выход add'а;
4. [moe.py:330](../../../python/freetoken/layers/moe.py) decode_submit:
   D2H маршрутизации -> doorbell пула L+1;
5. copy_missing (:338) + GEMM (:341) прячутся под окно пула L+1.

Каждая стрелка здесь - истинная зависимость по данным (выход предыдущего
узла = вход следующего). CUDA-graph здесь ничего не "запёк лишнего":
capture ([graph.py:149-211](../../../python/freetoken/engine/graph.py))
фиксирует ровно этот порядок, replay (:216-222) его повторяет; хост-код
модели на шаг не выполняется. Разница "запечённый порядок" vs "истинная
зависимость" существенна: перестановкой узлов графа выиграть нельзя -
независимых пар ресурсов в цепочке нет (единственная пара CPU-пул vs
PCIe-фетч уже совмещена, раздел 2.2). Единственная "не-дата" задержка во
всём шаге - doze-диспетч координатора pool1 (2.3), который лечится без
касания графа.

## 5. Кандидаты (ранжирование)

### C1. Doze-fix координаторов минорных пулов (НОВЫЙ)

- Что меняется: координатор выходит из doze, если ЛЮБОЙ экзекьютор кампании
  видел флаг недавно (общий hot-сигнал), либо env-ручка
  FREETOKEN_CPU_MOE_COORD_HOT_MS (0 = не спать, пока активен flag-sync;
  default 50 = текущее поведение). Файлы: cpu_moe_ext.cpp coordinator_loop
  (:2921-2960), проброс опции в cpu_executor.py start_flag_coordinator (:2903).
- Потолок: 1.308 -> ~0.3-0.4 => минус 0.9-1.0 ms/шаг: 56.7 -> ~55.8 ms =>
  16.86 -> ~17.1-17.2 tok/s = **+1.6-1.8%**.
- Риск: почти нулевой по корректности (тайминги, не данные; граф не
  пересобирается). Единственная цена - питание: doze существует ради
  edge-device idle (<0.1% ядра в простое); общий hot-сигнал сохраняет
  простой (пул молчит - все спят).
- A/B: одна переменная, серийные руки run_arm.py, 2 руки C1 + контроль в
  одном окне; ожидание сдвига именно грани p0->p1: 1.31 -> <=0.45 в трейсе
  (дешёвый дискриминатор ещё до e2e).

### C2. Fused submit: 3 D2H -> 1 на слой - ОПРОВЕРГНУТ nsys

- Идея: слить x/ids/w в один pinned-стейджинг
  ([cpu_executor.py:963-966](../../../python/freetoken/moe/cpu_executor.py)).
- Измерение (раздел 3): ВСЕ cudaMemcpy шага - 0.13 ms суммарно (D2H 127 шт -
  submit'ы и логиты; H2D 52 - результаты пулов). Гипотетический потолок
  0.4-1.2 ms не существует: реальный ~0.05-0.1 ms. Рычага нет.

### Закрытые кодом/данными кандидаты брифа

- (i) сайд-стрим фетч с join'ом перед MoE-ядром - УЖЕ ПРОДАКШН (2.2):
  потолок 0. Оценка ov0 (-23.5%) - верхняя граница того, что давал бы
  этот механизм, если бы его не было.
- (ii) prefetch слоя N+1 во время ожидания пула N - окна не существует:
  miss-сет L+1 становится известен только после router(L+1), который ждёт
  flag(L) (цепочка раздела 4). Спекулятивный межшаговый вариант - это
  семейство кеш-политики, убитое оракулом T3 (oracle_hit 25.7% против
  LRU 25.1%; ws 184/288 при ~8.6 слотах/слой - дефицит слотов, не порядок
  выборки).
- (iii) одна fused-копия всех миссов шага на старте шага - та же
  data-dependency (миссы слоёв 1..41 неизвестны на старте); пер-слойный
  fuse уже есть: FREETOKEN_FUSED_COPY=1
  ([offload_cache.py:15](../../../python/freetoken/moe/offload_cache.py)),
  fast_index_copy_multi_jit в copy_missing (:1057+).
- (iv) новое из структуры кода - только C1/C2 выше. Сплит-объём, флаг-sync,
  кеш-политика, AVX-512, больший фетч - подтверждённые не-рычаги
  (TASK.md), не реанимируются.

### Вне рамок задачи (policy-вопрос к пользователю)

Серийная GPU-цепочка ~11.8 ms (37 граней pool0) - теперь ИЗВЕСТНА как
критический путь (ранее считалось, что GPU-цепочка "полностью перекрыта").
Её ускорение (DSA-кернел, dense) формально попадает в опровергнутое
семейство "GPU math / FlashAttention" (FA архитектурно N/A для GDN+DSA).
Анатомия меняет обоснование запрета: цепочка не перекрыта; самое крупное в
ней - dense_gemv 6.7 ms/шаг (q8_0 MMVQ-проекции), затем KDA/mhc 1.9;
DSA-ядра - всего 0.3 ms/шаг. Решение о снятии запрета - не в этом документе.

## 6. Рекомендация

A/B первым - **C1 (doze-fix)**: минимальный диф (константа/ручка + общая
hot-метка), нулевой риск корректности, встроенный дешёвый дискриминатор
(грань p0->p1 в трейсе), воспроизводимость на существующем харнесе.
C2 опровергнут измерением (0.13 ms/шаг всех memcpy) - не кандидат.

Честное ожидание: C1 даёт +1.6-1.8%, что НИЖЕ гейта +5% из TASK.md.
Позитивный результат для принятия (та же планка, что wave 1): декод >= +5%
на >= 2 руках - вероятно, НЕ будет достигнут одной C1; осмысленные
варианты: (a) принять C1 как микро-коммит с честной формулировкой
(+~2%, нулевой риск), (b) повторить руки C1 во втором окне для подтверждения
устойчивости и затем решать, (c) не принимать и закрыть lever #2 с вердиктом
"гэпы - это серийная цепочка, перекрывать нечего". Префилл: C1 decode-only
(координаторы пулов не участвуют в префилле), допуск +/-1% сохраняется;
батарея 24/24 (kb/harness/quality/run_battery.py) обязательна, e2e-bitwise
не гейт (boot-to-boot недетерминизм).
