# Офлайн-кривая "слоты -> покрытие" (гейт ёмкостных рычагов)

## Goal

Построить офлайн (без GPU) кривую C(S): покрытие горячего окна декода в
зависимости от числа VRAM-слотов экспертов, из трейса маршрутизации. Цель -
решить, стоит ли вообще реализовывать источники дополнительных слотов
(перенос части KV-кеша в RAM по образцу Strata `--kv-resident`, увеличение
memory-ratio и т.п.) без кернельной работы наугад, и получить численный
верхний предел выигрыша каждого из них.

## Мотивация и фон

- Главный кандидат - KV-стриминг: обзор опыта Strata/Maya -
  [../../topics/strata-maya-inference-study.md](../../topics/strata-maya-inference-study.md).
  Оценка потенциала (~+200-300 слотов на перенос половины KV-квоты) - прикидка
  по документам Maya, не измерение; фактические числа (текущий фонд слотов S0
  и KV-квота) взять из бут-лога cache_budget текущего конфига.
- Урок кампаний 2026-09-26: бенч-прикидки (оффлоад gather-gap, "26.9 GB/s
  эффективных") дважды разбивались об инструментировку. Ёмкостный рычаг обязан
  пройти офлайн-оценку до реализации - тем более что реализация здесь
  (RAM-gather ячеек KV внутрь DSA-attention) дорогая и Maya её не сделал.

## Scope

**Входит:**

- Ф0 - аудит существующей телеметрии выбора экспертов: достаточно ли
  per-step пар (слой, эксперт) дают collect_stats / collect_decode_freq
  (T1-драйвер, зеркал в [../../harness/decode-research/README.md](../../harness/decode-research/README.md))
  и enable-cache-report, или нужна точечная инструментировка дампа.
- Ф1 - сбор трейса маршрутизации на одном исследовательском boot точного
  конфига пользователя (метод run_arm.py из харнесса выше: fill 64k +
  radix-reuse + greedy декод >= 768 токенов); запись expert_ids на каждый
  шаг декода.
- Ф2 - офлайн-симулятор политики резидентности (numpy/torch, CPU):
  LRU-recency по парам (слой, эксперт), пулы и слот-разделение по pool_policy,
  кап-доля fetch как в проде; sweep S.
- Ф3 - таблица C(S) и cpu_gib_per_step(S); валидация точки при S0 против
  телеметрии прод; вердикт по гейту.

**Не входит:** реализация KV-стриминга или route affinity; A/B на железе
(только после гейта); качество ответов; route affinity как таковая (см. ниже).

## Specification

- **S sweep:** {S0 (из бут-лога), S0+100..S0+600 шагом 100, 2*S0, все 12096
  пар} при фиксированных пулах pool_policy текущего конфига.
- **Метрики:** C(S) = доля пар (слой, эксперт) шага, обслуженных из VRAM-слотов
  (по всем шагам окна; отдельно медиана по шагам); cpu_gib_per_step(S) =
  суммарный байтовый объём перелива CPU-ноге. Проекцию на tok/s делать только
  через модель стоимости шага
  ([../../topics/moe-hybrid-cost-model.md](../../topics/moe-hybrid-cost-model.md))
  с явной пометкой "проекция, не оракул" - вердикт по гейту принимать по C(S),
  а не по проекции.
- **Валидация:** симуляция при S0 должна воспроизвести телеметрию hit-rate
  той же конфигурации с расхождением <= 2 п.п. (порог утвердить на Ф2).
  Якорь кампании "покрытие ~0.50 на 64k" получен на конфиге 0.82/400k -
  слепо не переносить; в конфиге 0.81/800k фонд слотов и квота KV другие.
- **Входные данные:** один трейс детерминированного greedy-декода; семплинг
  температурой запрещён (недетерминированный роутинг ломает сравнимость S).
- **Гейт решения (утверждается до Ф2):** +300 слотов дают < +5 п.п. покрытия
  -> KV-стриминг закрыт NO-GO без реализации; >= +8 п.п. -> бриф на прототип;
  между - решение владельца.
- **Риски:** симуляция политики != прод (закрывается валидацией точки при S0);
  дамп expert_ids замедляет шаг (только исследовательский boot, хук через env
  по образцу FREETOKEN_DECODE_RESEARCH-драйвера, обычные boot'ы не затронуты).

## Acceptance

- Таблица C(S) и cpu_gib_per_step(S) по всем точкам sweep, с конфигурацией
  и источником трейса.
- Валидированная точка при S0: симуляция vs телеметрия прод, дельта в п.п.
- Вердикт по гейту (NO-GO / GO на прототип / решение владельца) записан
  в этот каталог отдельным файлом.
- По завершении кампании: скрипты Ф2 (и Ф1, если дописывался драйвер)
  зеркалятся в kb/harness/<имя>/, отчёт - в этот каталог (правило
  самодостаточности kb).

## Checklist

- [ ] Ф0: аудит телеметрии - вердикт "трейс есть / нужна инструментировка"
- [ ] Ф1: трейс собран; конфиг, длина окна и число шагов зафиксированы
- [ ] Ф2: симулятор проходит валидацию при S0 (дельта <= 2 п.п.)
- [ ] Ф3: таблица C(S) + cpu_gib_per_step(S) + вердикт по гейту
- [ ] Зеркало артефактов в kb

## Примечание про route affinity

Офлайн-кривая отвечает на вопрос "что даёт ёмкость слотов при текущем
роутинге". Route affinity меняет сам роутинг (смещает выбор к резидентным
экспертам), поэтому трейсом прод не покрывается - мерить отдельной рукой
с env-флагом на железе + батарея качества, после вердикта Ф3.
