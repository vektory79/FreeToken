# Обновление ветки vektory79 мерджем origin/main (оркестрация)

Ты — оркестратор: обновляешь ветку vektory79 мерджем origin/main через волны субагентов
(discovery -> merge -> verify -> review -> triage/fix -> STOP GATE), не выполняя опасные
git-операции и тяжёлые прогоны самостоятельно.

## Критические ограничения

- ЗАПРЕЩЕНО всегда: `git push`, `gh pr create`, `gh pr comment`, `gh issue create`,
  `git rebase`, `git reset --hard` на пользовательских ветках, переписывание истории,
  force-push, удаление веток пользователя.
- История НЕ переписывается: только merge (никогда rebase), мерджи веток сохраняются как мерджи.
- РОВНО ОДИН merge-коммит за прогон ("Merge branch 'main' into vektory79"). Пост-ревью фиксы
  - только `git commit --amend` в merge-коммит (до push, parents сохраняются). Любые другие
  коммиты - только по явной просьбе пользователя.
- Правило дубликатов (директива пользователя): если функциональность main дублирует
  функциональность ветки - используется main, дубль ветки отбрасывается. Каждый случай
  фиксируется в adaptation-log с путями и обоснованием.
- `.veai/*` НИКОГДА не попадают в коммиты: `git add` только явными путями.
- Тесты прогоняются ДО финализации merge-коммита (merge --no-commit -> тесты -> commit).
- Пользователь обязан смочь объяснить каждую строку: все конфликтные решения и дубликаты -
  в adaptation-log с file:line.
- Субагенты (обязательны, руками git-мутации не делать):
  - `call_code_agent` - discovery, merge-волна, triage/fix;
  - `call_review_agent` - ревью разрешений;
  - `call_test_agent` - только если нужно расширить покрытие (обычно не нужно: тесты гоняет
    merge-волна). Ожидаемый результат call_test_agent: краткое резюме прогонов + путь к
    отчёту о тестах в task-каталоге (одна форма для всех его вызовов).
- Lean-контекст (правило затрат): в `context` субагента - только точные пути артефактов,
  file:line якоря и решения; содержимое файлов субагент читает сам по пути. Resume
  (`resume_id`) - только когда субагент уже держит нужные файлы и дельта задачи мала.
- Process-hygiene обязательна для любой волны, порождающей процессы (pytest, ft serve):
  census до/после, trap+watchdog runner, сериализованность, SIGTERM->30s->SIGKILL.
- Лимит quality-циклов: Review x2 -> Triage -> Fix TP - не более 3 циклов на логическую
  волну; не сошлись - стоп и отчёт пользователю (что сделано, TP/FP вердикты, варианты).

## Входные данные (разреши до старта)

1. Целевой ref: пользователь может сказать "origin/main" или "origin/master" - оба варианта
   валидны как запрос; фактический ref резолвит discovery (шаг 2). Если существуют ОБА
   origin/main и origin/master и оба ушли вперёд - NEEDS-USER-DECISION, вернись к пользователю.
2. Ветка: vektory79. Если `git branch --show-current` другой - стоп и уточнение у пользователя.
3. Task-каталог: `.tasks/merge-main-roundN-work/` (N = следующий за существующими round-каталогами).
4. Подтверди набор правил из "Критические ограничения" (пользователь мог изменить директивы).

## Алгоритм

### Wave 0 - память и артефакты

1. Прочитай из Memory Bank всё релевантное (merge-уроки, process-hygiene, pytest/serve
   gotchas, boot-эталоны) - описания в индексе; тела по необходимости.
2. Создай task-каталог (или переиспользуй пустой round-каталог).

### Wave 1 - discovery (call_code_agent, профиль fast, READ-ONLY + разрешён fetch)

Разбиение задачи: одна роль, один агент; запрещены merge/checkout/stash/commit/push.
Ожидаемый результат: компактная сводка в report_result + полный отчёт в
`<task>/discovery-report.md`. Собрать:

1. `git fetch origin` (упал по сети - работать по remote-tracking, пометив свежесть).
2. Резолв цели: существуют ли origin/main и origin/master, какой ушёл вперёд от последнего
   известного main-коммита; merge-base HEAD..цель.
3. Новые коммиты: полный `--name-only` список от базы до цели.
4. Конфликт-кандидаты: файлы новых коммитов ∩ `git diff --name-only <base>..HEAD`; для
   каждого - трогали ли его последние локальные коммиты ветки (или тронут только старым уже слитым дельта-коммитом).
5. Зоны риска (если задеты - mandatory boot-smoke в Wave 2, см. триггер):
   (a) hf_config-мутации: engine/config.py, mm/config.py (frozen GgufConfigShim ломается от
   setattr - исторический краш ВСЕХ gguf-бутов); (b) models/gguf/*; (c) планировщик MoE
   (engine/cache_budget.py, _split_moe_cache_budget, слот-гейт); (d) models/weight.py и
   glm5_next (общие пути загрузки).
6. State flags: чистота дерева (грязь ожидается только в .veai/*), `git stash list`
   (перепроверь дважды - наблюдались исчезающие stash-записи при параллельных сессиях),
   незавершённые операции (.git/rebase-*, MERGE_HEAD), HEAD-коммиты поверх ожидаемых
   (например пользовательские Memory-коммиты - принять как есть, не откатывать).

### Выбор режима

- Если discovery показывает конфликты/дубликаты, требующие дизайн-решений вне правила
  дубликатов - ESCALATE: короткий план + явный вопрос пользователю до Wave 2.
- Иначе DIRECT_EXECUTION: краткий план волн в чат (без отдельного approval) и вперёд.

### Wave 2 - merge-волна (call_code_agent, профиль strong)

Ожидаемый результат: merge-commit hash, решения конфликтов, счётчики тестов, smoke-вердикт,
инварианты + артефакты. Передай: путь discovery-отчёта, правила ограничений, эталонные
boot-числа из памяти (если есть). Шаги агента:

1. Preflight: статус чист (грязь только .veai/* - pathspec-stash их и pop после финализации),
   нет незавершённых операций. Stash НЕ пуст - СТОП и отчёт (чужие записи не терять).
   Backup: `git branch backup/vektory79-pre-mergeN-<short-sha>`.
2. Baseline-артефакты: список коммитов и diff-stat от базы (в task-каталог).
3. Локальный main вперёд только fast-forward: `git fetch origin main:main`; не ff - СТОП и отчёт.
4. ВСЕГДА начинай с `GIT_EDITOR=true git merge main --no-commit` (никогда не plain merge).
   Конфликты - разрешай (шаг 5); аварийный выход ДО коммита - `git merge --abort` (безопасно).
   Если merge-коммит всё же создан случайно - единственный разрешённый откат:
   `git reset --hard ORIG_HEAD` (дерево чистое, backup создан), затем повтори с --no-commit.
5. Разрешение конфликтов (если есть): union для дизъюнктных регионов; main-wins для
   дубликатов; СЕМАНТИЧЕСКАЯ проверка общих файлов - не отключил ли main пути ветки
   (пример: переписанный keep-filter load_weight vs наш load_gguf_moe_expert_sources).
   Всё - в adaptation-log.md (task-каталог).
6. Верификация ДО финализации:
   a. Conflict-marker grep по python/ tests/ docs/ - пусто.
   b. Целевые тесты (сериализованно, каждый под timeout, pre/postflight census
      `pgrep -af 'pytest|ft serve|benchbw|ft_run'` + `ls /dev/shm | grep -c "^sem\.mp-"`
      (матч собственной census-обёртки отфильтровывай), чужие живые процессы НЕ убивать):
      пиновые тесты ветки (gguf-banks, glm5_next,
      qwen3_vl, qsa-набор, tests/engine), новые тесты из main-коммитов, import-smoke.
      Запуск строго `uv run --extra dev python -m pytest` (не консольный pytest - import-режим
      глотает repo-root из sys.path и даёт ложные ModuleNotFoundError).
      ВЕТКА НА ПАДЕНИЯ: известный baseline или конкуренция чужой GPU-волны (Environment) -
      классифицируй и продолжай; НОВОЕ падение, не объяснимое этими классами - triage ДО
      финализации, фикс через amend (как шаг d); причина неочевидна - СТОП и отчёт.
   c. BOOT-SMOKE, триггер: merge затронул ЛЮБУЮ зону риска из Wave 1, п.5 (a)-(d) - тогда
      обязателен; иначе опционален. Рецепт: port 18081 (18080 занят wrapper-ом пользователя),
      `<репозиторий>/.venv/bin/ft serve` + рабочая конфигурация пользователя (актуальную взять
      из памяти, например gguf-786k: --moe-cache-auto --kv-reserve-tokens 786432
      --kv-cache-dtype nvfp4 --memory-ratio 0.89 --max-prefill-length 4096 --moe-strategy
      hybrid --moe-cpu-threads 16), trap-on-EXIT runner + FAILPAT-часовой
      ('AssertionError|OutOfMemoryError|Backend worker is gone|backend worker .* exited|Traceback|CUDA error|ValueError'),
      hard timeout 900s. Успех: /ready==200, boot-числа согласуются с эталоном по инвариантам
      (см. ниже), POST /v1/chat/completions с полем "model" (без него 422; max_tokens=8 даёт
      пустой content из reasoning-парсера - НЕ ошибка; HTTP 200 + usage = успех),
      SIGTERM shutdown (exit 143 штатен), VRAM к baseline, census чист.
      Если backend умер, а uvicorn висит в "Waiting for connections to close" - kill -9
      дерева принудительно (graceful не завершится).
      Boot-числа (слоты/KV) ЗАВИСЯТ от стартовой свободной VRAM - сравнивай инварианты:
      слот-гейт молчит, суммарные слоты >= рабочего набора, "больше свободно = безопаснее",
      а не точные числа.
   d. Если boot-smoke упал ПО ПРИЧИНЕ МЕРДЖА - семантическое разрешение в соответствующем
      файле допустимо (amend, повторный smoke); если причина неочевидна - СТОП: полный
      traceback в отчёт, решение за оркестратором/пользователем (сам merge не откатывать).
7. Финализация: `git add` только правленных файлов (явные пути) -> `GIT_EDITOR=true git commit`.
   Инварианты: `git rev-list --count HEAD --not <old-HEAD> <цель>` == 1; parents ==
   (old-HEAD, цель); .veai в коммите 0. Пост-финализационные фиксы - amend.
8. `git stash pop` (если был pathspec-stash), финальный census.

### Wave 3 - review (call_review_agent)

- SKIP допустим только при ВСЕХ условиях: конфликтов 0 И дизъюнктность регионов подтверждена
  чтением файлов И все тесты зелёные И boot-smoke зелёный (когда сработал). Обоснование skip -
  в финальный отчёт.
- Иначе: 2 параллельных прохода - A (correctness: эквивалентность разрешений обеим сторонам,
  семантика общих файлов, дубликаты по правилу main-wins) и B (edge: конфликт-маркеры,
  инварианты, тест-гэпы, доки-vs-код). Ожидаемый результат каждого: нумерованные findings
  [file:line] severity + evidence + явные вердикты по каждому фокусу.
- Если ревьюер должен гонять тесты - process-hygiene обязательна; полные suite-прогоны не
  дублировать (только точечные, по извлечённым спискам).

### Wave 4 - triage + fix (call_code_agent, resume автора merge-волны)

1. Каждая finding -> TP / FP / Need more data с обоснованием из текущего кода.
2. Фикс только TP; правки - amend в merge-коммит; тесты по фиксу точечные.
3. Не сошлись за 3 цикла - стоп, отчёт пользователю.

### Wave 5 - STOP GATE, память, финал

STOP GATE (всё обязано быть true): тесты выполнены и все падения триажированы (известный
baseline / конкуренция волн (Environment) / исправлено); review выполнен или обоснованно skipped;
все findings прошли triage; подтверждённых TP нет; инварианты merge-коммита проверены;
нет незавершённых git-состояний; артефакты записаны; kb-distill вызван: инсайты волны
дистиллированы в kb/ (навык [kb-distill](../kb-distill/SKILL.md); дайджест записанного
и пропущенного приложен к закрытию).
Затем: обнови Memory Bank durable-уроками (что нового узнала сессия: новые корневые причины,
ловушки, пересчёты ёмкости - не changelog). Финальный отчёт - см. Формат вывода.

## Формат вывода

Финальное сообщение пользователю, по пунктам:

1. Merge-commit hash + parents; состояние истории (история не переписана, мерджи сохранены).
2. Конфликты: файлы + решения (или "0 конфликтов"); дубликаты main-wins с путями (или "нет").
3. Тесты: команды + счётчики (passed/failed/skipped), классификация падений.
4. Boot-smoke: вердикт + boot-числа vs эталон (или "не требовался" + почему).
5. Ревью: пройден/обоснованно пропущен; findings -> triage -> что исправлено.
6. Инварианты (rev-list count, parents, .veai=0).
7. Пути артефактов (task-каталог: discovery-report.md, adaptation-log.md, test-results.md).
8. Открытые пункты и опции (push - за пользователем; backup-ветки; follow-up).

## Приёмочный чек-лист

- [ ] Целевой ref резолвлен discovery-агентом (origin/main vs origin/master), неоднозначность -> вопрос пользователю.
- [ ] Ровно один merge-коммит; parents корректны; rev-list count == 1; история не переписана.
- [ ] Дубликаты разрешены в пользу main и перечислены (или "нет дубликатов").
- [ ] Все конфликты задокументированы в adaptation-log (пользователь может объяснить каждую строку).
- [ ] Тесты прогнаны ДО финализации merge-коммита; падения триажированы (baseline/Environment/исправлено).
- [ ] Boot-smoke выполнен при сработавшем триггере зон риска; слот-гейт молчит на влезающих конфигах.
- [ ] Process-hygiene: census до/после, сериализованность, timeout-обёртки во всех прогонах.
- [ ] `.veai/*` в коммитах отсутствуют; push/gh не выполнялись.
- [ ] Review выполнен или пропущен по всем критериям skip с обоснованием; findings прошли triage; TP исправлены amend-ом.
- [ ] Memory Bank обновлён durable-уроками; финальный отчёт содержит все 8 пунктов.
- [ ] kb-distill вызван: инсайты волны дистиллированы в kb/ (навык kb-distill; дайджест
      записанного и пропущенного приложен к отчёту).
