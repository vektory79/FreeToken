# RTX 5090 на PCIe 5.0 x16: почему передача с хостом ограничивалась ~25 ГБ/с и как получить 46/57 ГБ/с

Дата расследования: 2026-09-12. Машина: work.vektory79.me.
Коротко: шина и железо всегда были исправны и честно обучались в PCIe 5.0 x16, но ядро Linux размещало GPU в IOMMU-домене с трансляцией адресов, и это душило DMA-поток вдвое. Исправление - один параметр ядра: `iommu=pt`. После него H2D вырос с 25.3 до 46.2 ГБ/с (+82%), D2H с 23.6 до 57.2 ГБ/с (+142%, это спецификация PCIe 5.0 x16).

---

## Часть 1. Рекомендации: что и где исправить

### 1.1 Основной фикс: `iommu=pt` в параметрах ядра

Файл `/etc/default/grub`, строка `GRUB_CMDLINE_LINUX_DEFAULT`:

```bash
sudo cp /etc/default/grub /etc/default/grub.bak

# Добавить iommu=pt в КОНЕЦ существующей строки (сохраняя все прочие параметры)
sudo sed -i 's/^GRUB_CMDLINE_LINUX_DEFAULT="\(.*\)"/GRUB_CMDLINE_LINUX_DEFAULT="\1 iommu=pt"/' /etc/default/grub

# Проверить глазами, что строка стала такой (пример с этой машины):
# GRUB_CMDLINE_LINUX_DEFAULT="quiet splash nvidia-drm.modeset=1 iommu=pt"
grep GRUB_CMDLINE_LINUX_DEFAULT /etc/default/grub

sudo update-grub
sudo reboot
```

Замечание к sed-команде: шаблон `\(.*\)` добавляет параметр в конец строки независимо от её содержимого. Простая замена вида `s/"quiet splash"/"quiet splash iommu=pt"/` молча промахивается, если в строке есть другие параметры (на этой машине был `nvidia-drm.modeset=1`) - это ловушка, в которую можно попасть при копировании инструкций из интернета.

### 1.2 Как проверить, что фикс применился (после перезагрузки)

```bash
# 1. Параметр реально передан ядру
cat /proc/cmdline
#    ... iommu=pt ...

# 2. Политика IOMMU-доменов по умолчанию - passthrough
sudo dmesg | grep -iE 'Default domain'
#    Ожидание: iommu: Default domain type: Passthrough (set via kernel command line)

# 3. IOMMU жив (не выключен целиком): у устройств есть группы
ls /sys/kernel/iommu_groups/ | wc -l
#    На этой машине: 18 (ноль означал бы полное отключение IOMMU)

# 4. Скорость вернулась
cd /media/ai/src/nvbandwidth/build
./nvbandwidth -t host_to_device_memcpy_ce | grep SUM   # ~46 ГБ/с, НЕ ~25
./nvbandwidth -t device_to_host_memcpy_ce | grep SUM   # ~57 ГБ/с, НЕ ~24
```

Быстрая проверка здоровья в будущем (например, после обновления ядра или BIOS) - первая строка из пункта 4: H2D должен быть ~46 ГБ/с. Если снова ~25 - фикс слетел.

### 1.3 Чего делать НЕ нужно

- **`intel_iommu=off`** - не использовать на постоянку. Скорость даёт ту же, но выключает IOMMU целиком: теряется изоляция DMA и проброс устройств в ВМ (VFIO). Если параметр уже добавлялся для теста - удалить его, оставить только `iommu=pt`. Держать оба параметра одновременно не нужно: конфигурация становится неоднозначной.
- **`setpci` для MaxReadReq GPU** (`setpci -s 01:00.0 CAP_EXP+08.w=...`) - проверено A/B на 256/512/1024/4096 байт: эффект ноль (в пределах шума ±0.25 ГБ/с) как до фикса, так и после. Оставить значение по умолчанию (256).
- **MaxPayload поднимать не пытаться** - у RTX 5090 аппаратный максимум 256 байт (`DevCap: MaxPayload 256 bytes`), это ограничение самой карты, а не системы.
- **BIOS ради этого не нужен** - проверено на свежей версии A.H0 (2025-06-04), обновление ничего не меняет.

### 1.4 Откат

Убрать `iommu=pt` из строки `GRUB_CMDLINE_LINUX_DEFAULT` и выполнить `sudo update-grub`. Система вернётся к Translated-доменам (и к ~25 ГБ/с).

## Часть 2. Почему это важно

### 2.1 Симптом: "идеальный линк, медленные данные"

Классические проверки ничего не находят: `lspci` показывает Gen5 x16 с обеих сторон, эквализация завершена, ошибок AER нет, `nvidia-smi` рисует 32 GT/s x16. А фактическая передача данных между GPU и RAM идёт со скоростью уровня PCIe 4.0 (~25 ГБ/с). Проблема тихая: ни один штатный индикатор о ней не сообщает.

### 2.2 Что такое IOMMU и причём тут скорость

IOMMU (Intel VT-d / DMAR) - аппаратный транслятор адресов DMA в корневом комплексе. Он переводит "устройственные" адреса, которые GPU ставит в своих DMA-запросах, в физические адреса RAM. Ядро Linux по умолчанию размещает устройства в **Translated-домене** - каждый DMA-запрос проходит через кэш трансляций (IOTLB) в чипсете.

Ключевой момент: у NVIDIA GPU **нет ATS** (Address Translation Services) - расширения, которым устройство само кэширует трансляции у себя. В `lspci -vv` у карты отсутствует Capability ATS. Значит, каждая транзакция GPU обслуживается транслятором в корневом комплексе.

Почему это режет скорость именно вдвое и одинаково для Gen4/Gen5: производительность DMA определяется не тактовой частотой провода, а количеством данных "в полёте" (in-flight bytes) при латентности пути:

```
скорость ~ (байт в полёте) / (RTT пути)
```

Транслятор ограничивает эффективное число одновременно обрабатываемых транзакций. При RTT ~600 нс это даёт ~25 ГБ/с - независимо от того, Gen4 на проводе или Gen5. Поэтому цифры RTX 5090 на Gen5 были неотличимы от цифр RTX 4090 на Gen4: обе упирались в одно и то же, и это было не шина.

### 2.3 Почему `iommu=pt`, а не полное отключение

`iommu=pt` ставит passthrough-домен по умолчанию: DMA-адреса устройств проходят **мимо трансляции** (identity mapping), что даёт ту же скорость, что и полное отключение. При этом сам IOMMU остаётся активен:

- сохраняется изоляция DMA - устройство не может записать в память, ему не назначенную (защита от DMA-атак и от случайных багов драйверов);
- работает проброс устройств в виртуальные машины (VFIO) - домены для привязанных к ВМ устройств создаются как обычно;
- остаётся irq remapping.

Полное отключение (`intel_iommu=off`) отдаёт то же самое за цену потери всех этих свойств - поэтому как постоянное решение не годится.

### 2.4 Кого касается

Consumer-платформы Intel (LGA1700: Raptor Lake и соседи) с NVIDIA-картами: GPU без ATS + Translated-домен по умолчанию = скрытая потеря примерно половины пропускной способности DMA. На серверных платформах или с устройствами, умеющими ATS, поведение может отличаться. Если после обновления ядра политика доменов по умолчанию изменится - симптомы вернутся (см. чек-лист 1.4/1.2).

### 3.2 Главный A/B-эксперимент: IOMMU Translated vs `iommu=pt`

Метод: идентичные прогоны nvbandwidth до и после перезагрузки с изменённым только параметром ядра.

| Тест | Translated (было) | `iommu=pt` (стало) | Прирост |
|---|---|---|---|
| H2D, copy engine | 25.28 ГБ/с | 45.95-46.20 ГБ/с | +82% |
| D2H, copy engine | 23.59 ГБ/с | 57.12-57.21 ГБ/с | +142% |
| Латентность GPU->RAM (pointer chase) | 617.5 нс | 601.3 нс | ~0% |

Разбег между повторами одного режима ~0.2-0.3 ГБ/с, так что приведённые диапазоны - шум.

Чего коснулись только "до" (после фикса эти тесты повторно не прогонялись, они не критичны):

| Тест | Translated (было) |
|---|---|
| Двунаправленный H2D+D2H CE (сумма) | 14.73 + 14.79 = 29.5 ГБ/с |
| SM-путь H2D / D2H | 7.23 / 8.79 ГБ/с |
| SM zero-copy (собственный кернел) | 10-12 ГБ/с |

### 3.3 Как читать эти числа

- **D2H 57.2 ГБ/с = ~91% полезной нагрузки Gen5 x16** (сырой провод 63 ГБ/с с учётом кодирования 128b/130b). Спецификация подтверждена: шина работает как заявлено.
- **H2D 46 ГБ/с (~73%) - нормальная асимметрия платформы.** D2H - это "posted"-записи (огонь и забыл), H2D - non-posted чтения, требующие ответа (round-trip). На клиентских чипах Intel это устойчивая характеристика платформы, не дефект: MRRS-эксперимент (ниже) на неё не влияет.
- **Двунаправленный тест до фикса (14.7 + 14.8 = 29.5 суммарно при 25.3 + 23.6 по отдельности)** - доказательство единого ограничителя на оба направления: если бы направления упирались в независимые лимиты (например, раздельные пороги DRAM), сумма была бы ~49 ГБ/с, а не ~29.5.
- **Латентность pointer chase не изменилась при фиксе (617 -> 601 нс)** - RTT пути доминировал и до, и после; узким местом при Translated-режиме был не RTT, а пропускная способность транслятора. Это объясняет, почему проблема "невидима" для латентностных тестов.

### 3.5 Служебные наблюдения (чтобы не путать будущих диагностов)

- `nvidia-smi` в простое показывает Gen1/Gen2 - это энергосбережение (линк опускается, когда GPU неактивна). Под нагрузкой линк честный Gen5 x16. Оценивать скорость линка надо под нагрузкой.
- Ошибки `VF BAR ... can't assign; no space` в dmesg - это SR-IOV и назначение VF-BAR'ов, на скорость DMA не влияют.
- MPS по пути: корневой порт DevCap 256, GPU DevCap 256 -> working value 256. Корректная конфигурация, менять нечего.
- ASPM отключён BIOS-ом (FADT) - на пропускную способность не влияет, трогать не нужно.

- Скрипты замеров: `.tasks/pcie-bw-probe/` в проекте FreeToken:

## Резюме

Проблема была не в карте, не в слоте, не в BIOS и не в памяти: линк Gen5 x16 тренировался безупречно, а DMA-движок душился трансляцией IOMMU в Translated-домене. Один параметр `iommu=pt` вернул спецификацию PCIe 5.0 x16 (46/57 ГБ/с) с сохранением работающего IOMMU. Все остальные переменные по ходу проверены и исключены - полный список опровергнутых гипотез в 3.4.
