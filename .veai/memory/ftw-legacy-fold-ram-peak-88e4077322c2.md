# FTW legacy carrier boot RAM peak: fold double-buffer, 198 GiB vs 125.17 (2026-10-21)

User symptom: pre-merge tag 2026.10.17 booted the legacy FTW-vision carrier (glm5next, 42 MoE layers, E=288, 3 width signatures, banks 125.17 GiB: gate 36.51 + up 36.51 + down 52.15; real shapes gate/up [288,2048,1568], down [288,4096,1088]) fine; HEAD OOMs the whole system (>125 GiB extra) during expert materialization before KV L1 reserve.

Root cause (code-verified, HEAD 8bba8e5, checkpoint/ftw.py load_ftw_banks): carrier lacks "gguf_tensor_types" -> legacy branch. Allocation order: merged gate_up 42x[288,3616,1568] = 73.02 GiB mmap allocated up front (ftw.py:797-836) + scratch 84 banks (2 copies of gate+up, another 73.02 GiB) + down 52.15 read directly into final. Peak 198.2 GiB if fold lags behind the 8-worker O_DIRECT read pool (ftw.py:905-930); fold is eager-free per-layer (_pair_on_done, Lock added in residual wave) but competes with readers + cudaHostRegister. Old stack (b8c3794) read the same bytes directly into final banks (three-separate layout WAS live) -> peak exactly 125.17. Cache slots/KV/overlap floor are VRAM only; --disable-moe-prefill-overlap does not touch the RAM profile; session tier L1 (10 GiB) is lazy runtime, not boot.

Fixes (in order of preference):
1. Zero-scratch fold (code): affine dest remap so gate/up 2 MiB jobs land directly inside merged blocks (gxC=3.21 MiB >= chunk 2 MiB, dest_off = e*(g+u)C + off_in_e); peak = 125.17 exactly, minus 73 GiB of copying, faster boot. NOT yet implemented.
2. Reconvert the carrier with the current `ft checkpoint` (writes merged layout + gguf_tensor_types; conversion pipeline verified 52s/125G, layer_sink streaming, no OOM) -> fold branch never activates. Solves the user's carrier fully; cost: time + ~140 GB disk, use --mmproj to keep vision.
3. Knob workaround: FREETOKEN_BANK_POOL_WORKERS=1-2 slows reads below fold pace -> peak ~128-135 GiB, +20-40s boot.
NOT helpful: FREETOKEN_BANK_CUDA_ALLOC=1 (same pages), --disable-moe-prefill-overlap.

Verification plan (cloud window): sample VmRSS/VmHWM 1 Hz around the "Loading expert banks (FTW)" bar; A/B pool=8 (predict ~150-198) vs pool=2 (predict ~131); steady-state RSS after pin ~125.2+alpha. Uncertainty: fold backlog magnitude inferred, not measured; the A/B discriminates cheaply.

How to apply: any legacy gguf->FTW carrier booting on the new stack hits this; surfaced from user's own recipe (hybrid, kv fp8, 400k reserve, max-prefill 8191, session tier). Related: ft-offload-banks-pinned-host (PinPipeline pin-after-fill, no copy on pin), TRAPS T90 (fold pairing race).
