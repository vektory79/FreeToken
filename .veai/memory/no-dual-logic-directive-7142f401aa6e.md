# Директива: запрет двойных логик main vs vektory79 (2026-10-25)

Пользователь (после round-6 merge, при ревью kb/cases/round6-deferred-ports/TASK.md) жёстко: "Ты хочешь оставить ДВЕ логики одновременно? Из main и из моей? Так не пойдёт!". Правила:

1. Если механика уже есть в main - остаётся ТОЛЬКО логика main. Веточная (vektory79) функциональность: либо ИСПОЛЬЗУЕТ новую логику main, либо РЕ-ИМПЛЕМЕНТИРУЕТСЯ поверх неё как дельта. Дублирование логики запрещено.
2. Веточный код - референс-спека, не перенос verbatim: каждый портированный элемент сидит на main-примитивах (пример: gguf->FTW vision packing - тензоры из main iter_mmproj_weights, кэрриер через main _pack_kv, а не возврат веточного writer 7bc68b0).
3. ТЕСТЫ - тоже без дублей, и семантически: дедуп не по названиям тестов, а по семантике (утверждения, гарды, кейсы). Если тест ветки дублирует тест main семантически - тест ветки удаляется, остаётся main. Если кейс/условие ветки НЕ покрыт в main - его надо доимплементировать (адаптировать на main-механику), а не молча потерять.
4. Каждая фаза порт-долга начинается с классификации её skip-маркеров пробным прогоном: зелёные на main -> снять; семантический дубль main-теста -> удалить веточный тест (пара задокументирована); пин веточной семантики вопреки main-дизайну -> переписать тест под main; непокрытый кейс -> доимплементировать; пин отсутствующей дельты -> ждёт реализации.

**Why:** реакция пользователя на черновик TASK.md round 6, где D2-фаза записывалась как "вернуть веточную vision-механику" при полностью живой main mmproj-механике (iter_mmproj_weights, gguf_mm_config, find_mmproj).
**How to apply:** любой порт/ре-ленд после re-platform-мерджа; формулировки задач типа "вернуть X из ветки" переписывать в "ре-имплементировать X поверх main Y"; DoD фаз включает критерий "нет файлов с двумя логиками" и полную карту тестов (un-skipped/удалён/переписан/доимплементирован).
